# PersistentKeyValueKit 2.0.0 Release Notes

PersistentKeyValueKit 2.0.0 adds typed key migration within and between stores, checked format-aware conversion on representations and primitive types, `PersistentKeyProtocol` routing on `InMemoryPersistentKeyValueStore`, updated `URL` and collection rules, observation refinements across SwiftUI, `AsyncSequence`, Combine, and Foundation stores, and an Apple privacy manifest. Custom `PersistentKeyValueRepresentation`, `PrimitiveKeyValuePersistible`, and `PersistentKeyValueStore` conformances require new members, and `URL`, collection, and in-memory optional semantics change; see [Breaking Changes and Upgrade Guide](#breaking-changes-and-upgrade-guide).

## What's New

### Store-to-Store and Same-Store Key Migration

`PersistentKeyValueStore` adds `copy` and `move` overloads for migrating a single key, a single `PersistentKeyMigrationItem`, a heterogeneous array (`[any PersistentKeyProtocol]`), or a labeled array (`items: [PersistentKeyMigrationItem]`):

```swift
func makeAppGroupDefaults() throws -> UserDefaults? {
    guard let appGroup = UserDefaults.migratable(suiteName: "group.example.app") else {
        return nil
    }

    let report = try UserDefaults.standard.move(
        [.runtimeColorScheme, .launchCount],
        to: appGroup,
        onConflict: .keepBoth,
        tracking: .once(id: "app-group-preferences-v1")
    )
    try report.throwIfIncomplete()

    return appGroup
}
```

#### Key Mapping, Transforms, and Same-Store Rules

- `PersistentKeyMigrationItem` supports `.key(_:)`, `.key(_:to:)` for renaming keys of the same `Value` type, and `.key(_:to:transform:)` for converting values with an `@Sendable` throwing closure.
- `transform` runs after source decoding when both keys have `isMigrationEnabled == true` and the item writes to the destination. It skips `.sourceAbsent`, `.keyDisabled` (such as `PersistentDebugKey` in Release builds), and `.keptDestination` or `.discardedSource`.
- If `transform` throws, the item fails at `.transform` and writes to neither store, keeping the source on a `move`. An `InMemoryPersistentKeyValueStore` source passes the stored Swift value directly to `transform`, so copy a mutable reference before modifying it.
- Same-store migrations are supported when every item maps to a different destination key. In-place rewrites are not supported: mapping any key to its own identifier within one store (even with `transform`) throws `PersistentKeyMigrationError.sameStore` before reading any key.
- To change a key's stored representation or value format, `move` it to a new key identifier.
- Duplicate source or destination identifiers throw `PersistentKeyMigrationError.duplicateKey(_:)`. Same-store chains or swaps (`A` to `B` and `B` to `C`, or `A` to `B` and `B` to `A`) throw `PersistentKeyMigrationError.overlappingKeys(_:)`.
- In duplicate, overlap, and same-store checks, `UserDefaults` and `NSUbiquitousKeyValueStore` compare identifiers by literal UTF-16 code units (composed vs decomposed spellings and unpaired surrogates are distinct keys), while `InMemoryPersistentKeyValueStore` merges canonically equivalent spellings.

#### Domain Scope, Conflict Policies, and Retries

- Migration reads only values persisted in each store's own domain. Registered defaults (`UserDefaults.register`), launch arguments (`UserDefaults.argumentDomain`), added suites (`UserDefaults.addSuite(named:)`), and `defaultValue` are neither migrated nor treated as destination conflicts.
- Every `copy` requires `PersistentKeyCopyConflictPolicy` (`.keepDestination` or `.overwriteDestination`), and every `move` requires `PersistentKeyMoveConflictPolicy` (`.keepBoth`, `.overwriteDestination`, or `.keepDestinationAndRemoveSource`).
- After a `move` removes its source key, a retry finds `.sourceAbsent`. When a source value remains, `.keepDestination` and `.keepBoth` keep an existing destination value (including one written by an earlier attempt) without running `transform` while `.keepBoth` also leaves the source; `.overwriteDestination` reconverts the source and replaces the earlier result.
- `UserDefaults` and `NSUbiquitousKeyValueStore` do not preserve integer bit widths across processes or launches (`Int32` reads back as written in the writing process, and 64-bit elsewhere), so migration accepts any integer width when preparing writes.
- In-memory migrations detect concurrent edits to Foundation property-list objects (such as `NSMutableArray`), while other reference types are only detected when replaced, so do not mutate stored references during a migration.

#### Completion Tracking and Named Suites

- `PersistentKeyMigrationTracking` offers `.untracked`, `.once(id:)` (recorded in the destination store), and `.once(id:recordedIn:)`. Empty batches (`[]`) are valid and record completion when tracked.
- Completion markers use `.isMigrationCompleted(id:)`, fitting `NSUbiquitousKeyValueStore`'s 128-UTF-16-code-unit limit and `UserDefaults` KVO for any `id`. Identifiers equal as Swift strings share one marker (case differs); remove the key or set it to `false` to re-run, or pick a new `id` when changing a migration.
- A marker recorded in `NSUbiquitousKeyValueStore` syncs across devices; use `.once(id:recordedIn: UserDefaults.standard)` for once-per-device seeding. When migrating from `NSUbiquitousKeyValueStore`, use `.untracked` until initial sync populates the local cache so unsynced keys are not permanently marked `.sourceAbsent`.
- `UserDefaults.migratable(suiteName:)` returns a native `UserDefaults` with process-local domain metadata for its lifetime. It returns `nil` if empty, containing `/` or NUL, starting with `~`, ending with `.plist` (ignoring case), matching a reserved domain or `Bundle.main.bundleIdentifier` (ignoring case and normalization), or failing Foundation creation; migration treats case- and normalization-equivalent suite names as one store.

#### Reports, Failure Stages, and Concurrency Rules

- `copy` and `move` return a non-`@discardableResult` `PersistentKeyMigrationReport` with ordered `outcomes`, `completion` (`.recorded`, `.alreadyRecorded`, `.notRecorded` when an item fails under `.once`, `.failed` when marker recording fails, or `.untracked`), `completionError`, `hasFailures`, `isComplete`, `outcome(for:)` (matching `sourceKeyID` by literal UTF-16 code units), and `throwIfIncomplete()` (throwing `PersistentKeyMigrationIncompleteError`). Public fixture initializers enforce field invariants via preconditions.
- `PersistentKeyMigrationError` setup errors (`missingApplicationIdentifier`, `missingMigrationDomain`, `sameStore`, `duplicateKey(_:)`, `overlappingKeys(_:)`, `reservedKey(_:)`, `keyIdentifierTooLong(_:)`, `invalidMigrationIdentifier`, `overlappingMigration`, `invalidCompletionRecord`, plus `migrationEndpoint` errors) throw before accessing any key. Identifiers starting with `PersistentKeyValueKit_MigrationCompleted_` (including NFC-equivalent or combining-mark spellings) throw `reservedKey(_:)`.
- `.prepare` failures mean encoding or destination validation failed before modifying either store, such as for objects stores cannot persist or values altered by Foundation serialization (like `NSDecimalNumber` becoming `Double`, or lossy file URLs).
- `.write` failures mean writing the destination failed, or under `.keepDestination`, `.keepBoth`, or `.keepDestinationAndRemoveSource`, the existing destination value changed or vanished (leaving the source in place).
- Migrations never roll back completed writes. On `move` `.cleanup`, `.sourceChanged` keeps the source; `.destinationChanged` removes the source without rolling back the destination write; `.removalVerificationFailed` means the source still held a value after removal without rolling back the destination write.
- Coordinate other writers, processes, and reentrant code that writes to a migrating store as a side effect of reading, encoding, or deallocating a value (getters, `deinit`, allocator callbacks, or observers) before migrating; behavior with uncoordinated reentrant writers is unspecified.
- Local completion does not guarantee disk durability or iCloud delivery, and removing a key from `NSUbiquitousKeyValueStore` deletes it across the user's devices.

### Checked Representation Conversion

- `PersistentKeyValueRepresentation` and `PrimitiveKeyValuePersistible` add throwing `decode(storageObject:format:)` and `encode(_:format:)` / `encode(format:)` methods taking `PersistentKeyValueStorageFormat` (`.propertyList`, `.userDefaults`, or `.ubiquitousKeyValueStore`). Ordinary `get` and `set` stay non-throwing.
- Built-in conversion failures throw `PersistentKeyValueConversionError` (`.invalidStorageValue`, `.invalidValue`, or `.encodingFailed`), while `CodablePersistentKeyValueRepresentation` rethrows `Encoder` and `Decoder` errors. Proxy and `Codable` checked `encode(_:format:)` reject objects stores cannot persist (keyed-archive UIDs, `NSNull`, `URL`s, non-string keys, and cycles; store archives as `Data`) with `.encodingFailed` and verify round-trip decoding.
- Package representations (`Array`, `Dictionary`, `Optional`, proxy, `RawRepresentable`, `LosslessStringConvertible`, `Codable`, and built-in scalars) perform strict checked container conversions on any thread. Checked `Array` decoding reports errors in input order when all element representations and primitives are built in.
- Checked `Dictionary` conversion fails if any entry fails to decode or if a stored Foundation dictionary has canonically equivalent keys with different UTF-16 spellings, whereas ordinary `Dictionary` reads keep readable entries and keep one colliding entry.
- Custom `PersistentKeyValueRepresentation`, `PrimitiveKeyValuePersistible`, and `ProxyPersistentKeyValueRepresentationProtocol` types run their container methods (`get(from:)`, `set(_:to:)`, `get(_:from:)`, `set(_:to:in:)`) as written during checked conversion, so external proxies over `[String: Value]` inherit lenient nested dictionary reads unless overridden. External write output is validated as a property list across all formats.
- `URL` conversion supports absolute URLs and relative references. For `.userDefaults`, checked decoding matches `UserDefaults.url(forKey:)` and throws `.invalidStorageValue` for unreadable paths (empty or NUL), while checked encoding throws `.encodingFailed` for file URLs whose stored path cannot reproduce `url.absoluteString` (file URL host, empty path, or nonexistent directory trailing slash) across direct, `Optional`, and proxy keys.
- In `.userDefaults` and `.ubiquitousKeyValueStore` formats, checked `String.decode` converts stored `NSNumber` values using `number.stringValue` (`"1"` or `"0"` for Booleans), matching ordinary reads, while `.propertyList` accepts only strings. `Optional<String>`, `String`-backed `RawRepresentable`, `LosslessStringConvertible`, and proxy keys over `String` inherit this behavior.

### In-Memory Store Key Routing and Semantics

- `InMemoryPersistentKeyValueStore` now routes `get(_:)`, `set(_:to:)`, and `remove(_:)` through `PersistentKeyProtocol` (`get(from:)`, `set(to:in:)`, `remove(from:)`) backed by `object(forKey:)`, `set(_:forKey:)`, and `removeObject(forKey:)`.
- A key's value must live under `id` in every store so observation and migration act on the same entry; store-specific requirements customize how values are read, written, or gated, not where they are stored.
- `set(_:forKey:)` stores an explicit `nil` entry for optional keys (migrating stored `nil` to a Foundation store with `.overwriteDestination` removes the destination key). `nil` elements are compacted only out of Swift arrays and `String`-keyed dictionaries of optionals when the compacted type still matches `Value`, leaving Foundation collections such as `NSMutableArray` unchanged.
- `InMemoryPersistentKeyValueStore` retains and returns the Swift value itself, so use immutable or `Sendable` reference types across concurrency domains. In-memory-to-in-memory migrations transfer Swift values directly without calling representation codecs.

### Observation, Registration, and Launch Arguments

#### SwiftUI and `@PersistentValue`

- `@PersistentValue` updates its observed key and store when a view re-evaluates at the same identity with a different key identifier (compared by literal UTF-16 code units), explicit `store:`, or `defaultPersistentKeyValueStore` environment value.
- `PersistentKeyUIObservableObject.key` is now `public private(set) var`. Assigning a different `store` (or `nil`, or a value-type store) updates observation, stops notifications from the previous store (even queued cross-thread ones), and sends `objectWillChange`; reassigning the same reference store (or `nil` when already `nil`) is a no-op.
- Reading `PersistentKeyUIObservableObject.value` when `store` is `nil` returns `key.defaultValue`; writing without a store discards the write and asserts in Debug builds. Writes target the key and store active when the setter starts, and reentrant switches during replacement keep the latest selection.
- A `$binding` projected from `@PersistentValue` captures the active key and store weakly referencing the observer, so a retained binding written after the view switches keys or stores still reads and writes its original key and store without invalidating the view or keeping later stores or view state alive.

#### Literal Key Identity

- `UserDefaults`, `NSUbiquitousKeyValueStore`, `PersistentKey`, and `PersistentDebugKey` compare and hash key identifiers by literal UTF-16 code units, so composed vs decomposed spellings and identifiers differing only in unpaired surrogates (such as truncated emoji from `NSString.substring(to:)`) remain distinct keys. `InMemoryPersistentKeyValueStore` merges canonically equivalent spellings.
- Because `PersistentKeyProtocol.ID` is `String`, SwiftUI's `ForEach(keys)` merges canonically equivalent spellings. Use `ForEach(keys, id: \.id.utf8CString)` to keep rows distinct; UTF-8 cannot represent unpaired UTF-16 surrogates, so identifiers differing only in unpaired surrogates still share a row. `\.self` is not a substitute because key equality also compares `defaultValue`.
- A Foundation-backed `PersistentKeyProtocol.id` must not access a store when its characters are read. Callbacks delivered during registration can deregister immediately, and deregistered observers receive no further notifications.

#### `AsyncSequence` and Combine

- `PersistentKeyValues` emits values read from the store in read order (never older than an already-emitted value), defaulting to `.bufferingNewest(1)` or `.unbounded` to buffer every observed change. When the iterating `Task` is cancelled before or during `next()`, `next()` deregisters, releases pending and buffered values, and returns `nil` on that and all subsequent calls.
- `PersistentKeyValuePublisher` reads the initial value on subscription and delivers synchronously on the thread requesting demand or reporting a change (or on the thread already delivering concurrent updates, so returning from a setter does not mean delivery finished). Inside `receive(subscription:)`, only the subscribing thread delivers values, so blocking there for another thread's delivery will hang. Use `.receive(on: DispatchQueue.main)` before updating UI.

#### Foundation Stores and Launch Arguments

- `UserDefaults` keys that KVO cannot observe (empty keys, leading `@`, `.`, NUL, and `valueForKey:` / `ValueForKey:`) now observe via `UserDefaults.didChangeNotification` across all observation APIs. They see only in-process property-list changes (not cross-process writes or `addSuite(named:)` / `removeSuite(named:)`), and changes are sampled: rapid writes coalesce, `A` to `B` to `A` changes undone before sampling can emit nothing, and consecutive values can be equal.
- Other `UserDefaults` keys use KVO and see cross-process changes, but Foundation posts no KVO notification when a write compares equal under Foundation equality (such as `Int64` over an equal `Int32`, or `-0.0` over `0.0`), so subscribers keep the previous numerically equal value until the key next changes.
- `NSUbiquitousKeyValueStore` observers refresh on external notifications reporting `NSUbiquitousKeyValueStoreAccountChange` or omitting `NSUbiquitousKeyValueStoreChangedKeysKey`, and `didChangeInternallyNotification` is posted with the writing instance as `object` (use `NSUbiquitousKeyValueStore.default` everywhere).
- `UserDefaults.register(_:)` and `registerDefault(in:)` encode defaults with `.userDefaults` format (skipping defaults that fail checked encoding) and preserve literal UTF-16 keys. Launch-argument coercion applies only when the visible value is the literal key's `UserDefaults.argumentDomain` string and is not overridden by a managed preference, so managed preferences take precedence and a launch argument for one Unicode spelling does not coerce a value stored under another spelling.

### Privacy Manifest

The `PersistentKeyValueKit` target bundles `PrivacyInfo.xcprivacy` declaring `UserDefaults` access (`NSPrivacyAccessedAPICategoryUserDefaults`) with reasons `CA92.1` (app-sandbox preferences) and `1C8F.1` (app-group preferences).

## Breaking Changes and Upgrade Guide

### 1. Direct `PersistentKeyValueRepresentation` Conformances

`PersistentKeyValueRepresentation` now requires `decode(storageObject:format:)` and `encode(_:format:)`. Its eight store- and container-specific `get` and `set` methods have default implementations built on those two methods; existing overrides still apply.

- **No changes required** if you use `ProxyPersistentKeyValueRepresentation`, `RawRepresentablePersistentKeyValueRepresentation`, `CodablePersistentKeyValueRepresentation`, `LosslessStringConvertiblePersistentKeyValueRepresentation`, or conform to `ProxyPersistentKeyValueRepresentationProtocol`.
- **Upgrade steps**: Implement `decode(storageObject:format:)` and `encode(_:format:)`, returning `nil` to remove the key, and do not mutate objects returned from `encode` or written by `set` afterward. Default `get` returns `nil` on absence or decode failure without launch-argument coercion; default `set` leaves the store unchanged if `encode` throws or returns an unsupported object (keyed-archive UIDs, `NSNull`, `URL`s, non-string keys, or cycles; store archives as `Data`).

```swift
extension CustomRepresentation: PersistentKeyValueRepresentation {
    func decode(storageObject: Any, format: PersistentKeyValueStorageFormat) throws -> Value {
        guard let string = storageObject as? String, let value = Value(parsing: string) else {
            throw PersistentKeyValueConversionError.invalidStorageValue
        }
        return value
    }

    func encode(_ value: Value, format: PersistentKeyValueStorageFormat) throws -> Any? {
        value.serializedString
    }
}
```

### 2. Custom `PrimitiveKeyValuePersistible` Conformances

`PrimitiveKeyValuePersistible` now requires `static func decode(storageObject:format:)` and `func encode(format:)`. Its eight store- and container-specific `get` and `set` methods have default implementations built on those two methods, using `.propertyList` for containers; existing overrides still apply.

- **No changes required** for built-in primitive types (`Bool`, `Int`, `Float`, `Double`, `String`, `Data`, `URL`, `Array`, and `Dictionary`) or `Optional`.
- **1.x behavior change**: Custom primitives using 1.x container defaults now write and read container elements through `encode(format: .propertyList)` and `decode(storageObject:format: .propertyList)`, so `decode` must accept any objects 1.x persisted in containers.
- **Upgrade steps**: Implement `decode(storageObject:format:)` and `encode(format:)` on custom `PrimitiveKeyValuePersistible` types.

```swift
extension CustomPrimitive: PrimitiveKeyValuePersistible {
    static func decode(storageObject: Any, format: PersistentKeyValueStorageFormat) throws -> Self {
        guard let number = storageObject as? NSNumber else {
            throw PersistentKeyValueConversionError.invalidStorageValue
        }
        return Self(rawValue: number.intValue)
    }

    func encode(format: PersistentKeyValueStorageFormat) throws -> Any? {
        NSNumber(value: rawValue)
    }
}
```

### 3. Custom `PersistentKeyValueStore` Conformances

`PersistentKeyValueStore` now requires `var migrationEndpoint: PersistentKeyValueMigrationEndpoint { get throws }`.

- **Upgrade steps**: Forward your backing store's `migrationEndpoint` (`try base.migrationEndpoint`), or throw your own error if the store cannot migrate (`copy` and `move` propagate it unchanged).

```swift
extension ForwardingStore: PersistentKeyValueStore {
    var migrationEndpoint: PersistentKeyValueMigrationEndpoint {
        get throws {
            try base.migrationEndpoint
        }
    }
}
```

### 4. `URL` Storage and Validation

Writing a `URL` to `NSUbiquitousKeyValueStore` now stores `url.absoluteString` (`String`) instead of a `URL` object, matching property-list requirements.

- Reading a `URL` from `NSUbiquitousKeyValueStore` in 2.0.0 accepts both `String` values and legacy 1.x `URL` objects.
- **Mixed-version iCloud compatibility**: 1.x clients read `URL` keys using `object(forKey:) as? URL`. When a 2.0.0 device writes a `URL` (`String`) and iCloud syncs it to a 1.x device, the 1.x client falls back to `defaultValue`.
- Ordinary `UserDefaults` `set` keeps Foundation's path storage, while checked `.userDefaults` decoding throws `.invalidStorageValue` for unreadable paths and checked encoding throws `.encodingFailed` for lossy file URLs across migration and `UserDefaults.register(_:)`. `[URL]` stores `absoluteString` in `.propertyList` format.

### 5. All-or-Nothing Collection Writes and Container Contracts

In 1.x, failed collection writes could overwrite part of a collection, and built-in `set(_:to: inout [Any])` appended to `propertyListArray` instead of replacing it.

- `Array` and `Dictionary` writes are now all-or-nothing across `UserDefaults`, `NSUbiquitousKeyValueStore`, and property-list containers, leaving the store unchanged if any element or entry fails to encode; `Optional` `nil` elements and entries are omitted.
- Built-in `set(_:to: inout [Any])` implementations replace `propertyListArray`. Callers pass an empty array to `set(_:to:)` and a dictionary missing `dictionaryKey` to `set(_:to:in:)`, keeping 1.x appending overrides compatible.
- **Handover contract**: Do not mutate an object after returning it from `encode`, returning it from a proxy `to`, or writing it via `set` (including mutable strings, data buffers, dictionary keys, or containers); behavior is unspecified otherwise.
- **Container hook contracts**: Array `set(_:to:)` hooks may only assign or append to the empty array passed in. Dictionary `set(_:to:in:)` hooks must write only `dictionaryKey` without reading, modifying, adding, or removing other entries.
- For external representations, leaving `propertyListArray` empty for non-empty input, leaving `dictionaryKey` absent, or writing unsupported objects (keyed-archive UIDs, `NSNull`, `URL`s, non-string keys, or cycles; store archives as `Data`) fails ordinary writes unchanged and throws `.encodingFailed` in checked conversion.
- Ordinary `Array` reads are all-or-nothing and ordinary `Dictionary` reads omit undecodable entries, while checked conversion fails on any element/entry error or colliding canonically equivalent keys for built-in types (external representations run their container methods as written).

### 6. Named `UserDefaults` Suites in Migrations

- Create any named `UserDefaults` suite passed to `copy`, `move`, or `.once(id:recordedIn:)` with `UserDefaults.migratable(suiteName:)`. `UserDefaults.standard` requires a non-empty `Bundle.main.bundleIdentifier` (otherwise throwing `.missingApplicationIdentifier`).
- Ordinary `UserDefaults(suiteName:)` instances continue to work outside migrations, but throw `PersistentKeyMigrationError.missingMigrationDomain` if used in a migration.

### 7. `PersistentDebugKey`, In-Memory Optionals, and Key Access

- `InMemoryPersistentKeyValueStore` now routes `get(_:)`, `set(_:to:)`, and `remove(_:)` through `PersistentKeyProtocol`, applying `PersistentDebugKey`'s Release lock (and skipping migration with `.keyDisabled`). Custom `PersistentKeyProtocol` types get in-memory defaults and must keep values under `id` in every store.
- Unset or removed optional keys in `InMemoryPersistentKeyValueStore` now return `key.defaultValue` (even when non-`nil`), whereas setting an optional key to `nil` records an explicit `nil` returned by `get(_:)`.
- `PersistentKey` and `PersistentDebugKey` `Equatable` and `Hashable` now compare `id` by literal UTF-16 code units, and `PersistentKeyUIObservableObject.key` is now `public private(set) var`.
