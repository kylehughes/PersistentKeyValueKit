# PersistentKeyValueKit 2.0.0 Release Notes

PersistentKeyValueKit 2.0.0 adds typed key migration between and within stores, introduces checked format-aware conversion on representations and primitive types, routes `InMemoryPersistentKeyValueStore` access through `PersistentKeyProtocol`, updates `URL` storage in `NSUbiquitousKeyValueStore`, and bundles an Apple privacy manifest.

## What's New

### Store-to-Store and In-Place Key Migration

`PersistentKeyValueStore` now provides `copy` and `move` overloads for transferring a single key, a single `PersistentKeyMigrationItem`, a heterogeneous array of keys (`[any PersistentKeyProtocol]`), or a labeled array of items (`items: [PersistentKeyMigrationItem]`):

```swift
func makeAppGroupDefaults() throws -> UserDefaults? {
    guard let appGroup = UserDefaults.migratable(suiteName: "group.example.app") else {
        return nil
    }

    let report = try UserDefaults.standard.move(
        [.runtimeColorScheme, .launchCount],
        to: appGroup,
        onConflict: .keepBoth,
        tracking: .once(id: "app-group-preferences-v1")
    )
    try report.throwIfIncomplete()

    return appGroup
}
```

- **Key mapping, transforms, and in-place rewrites**: `PersistentKeyMigrationItem` supports `.key(_:)`, `.key(_:to:)` for renaming a key of the same `Value` type, and `.key(_:to:transform:)` for converting values with an `@Sendable` throwing closure. The source and destination can be the same store when every item either maps its source key to a different destination key or rewrites a key in place through `.key(_:to:transform:)` with byte-identical source and destination key identifiers (`source.id.utf8.elementsEqual(destination.id.utf8)`). Duplicate source or destination key identifiers (including rewrites) throw `PersistentKeyMigrationError.duplicateKey(_:)`, and same-store batches where one item's destination is another item's source (such as `A` to `B` and `B` to `C`, or `A` to `B` and `B` to `A`) throw `PersistentKeyMigrationError.overlappingKeys(_:)`. Key identity in duplicate, overlap, and same-store checks follows the store: `UserDefaults` and `NSUbiquitousKeyValueStore` compare identifiers by literal UTF-16 code units (treating NFC and NFD spellings as distinct keys), whereas `InMemoryPersistentKeyValueStore` is keyed by Swift `String` and treats canonically equivalent identifiers as one key. Within a single store instance, an in-place rewrite decodes the stored value with the source key's representation, transforms it, encodes the result with the destination key's representation, replaces the stored value only if its snapshot has not changed, verifies the write, never removes the key as a source during a `move`, and reports `.rewritten` under every copy or move conflict policy (pass `transform: { $0 }` for a representation-only upgrade under the same key identifier). If a tracked batch is retried after a later item fails, a stored value that fails to decode with the source key's representation but decodes with the destination key's representation is treated as already rewritten and reports `.rewritten` without running `transform` or writing again; a rewrite must therefore change the stored representation or use an idempotent `transform`, whereas same-format value changes (such as dollars to cents) should move to a new key identifier. `.key(_:)` and `.key(_:to:)`, or a rewrite between two distinct instances for one backing store, throw `PersistentKeyMigrationError.sameStore`. `transform` runs after the source value decodes, when both keys have `isMigrationEnabled == true` and the item will write to the destination (for an in-place rewrite, when the destination key has no persisted value, or when `onConflict` is `.overwriteDestination`), and is skipped when the source is absent or a conflict policy keeps an existing destination value (`.keptDestination` or `.discardedSource`). If `transform` throws, the item fails at stage `.transform` and neither store is modified for that item, including during a `move`. Because `InMemoryPersistentKeyValueStore` stores Swift values directly, migrations between in-memory stores transfer the stored value by type cast without calling representation `decode` or `encode`.
- **Persisted-domain reads, conflict detection, and verification**: Migration inspects only values persisted in a store's own domain. Registered defaults (`UserDefaults.register`), launch arguments (`UserDefaults.argumentDomain`), added suites (`UserDefaults.addSuite(named:)`), and a key's `defaultValue` are not migrated from the source and do not count as destination conflicts. `UserDefaults` migration snapshots read the writable domain as an unbridged `NSDictionary` so keys are matched by literal UTF-16 code units (distinguishing canonically equivalent NFC and NFD key spellings, as Foundation does). Snapshot verification compares property-list types and floating-point widths (`Float` versus `Double`) as well as values recursively (so boolean `true` is not treated as equal to integer `1`), and `InMemoryPersistentKeyValueStore` snapshots compare the contents of Foundation property-list objects (such as `NSMutableArray`) while verifying other reference types by revision only. A `UserDefaults` write or rewrite that replaces a stored object with a `CFEqual` object of a different property-list type removes the old object first and fails at `.write` with `PersistentKeyMigrationError.destinationChanged` (preserving the observer's write) if an observer writes the key during removal. On a `move`, `.failed(.cleanup)` with `PersistentKeyMigrationError.destinationChanged` means the destination changed during cleanup: either before removing the source (when `.keepDestinationAndRemoveSource` found the kept destination value changed and left the source in place) or after removing the source (when an observer notified by source removal modified the destination); read the source key to tell whether it was removed.
- **Required conflict policies and tracking**: Every `copy` and `move` call requires an explicit conflict policy (`onConflict:`) and tracking mode (`tracking:`), with no defaults. Copy operations take `PersistentKeyCopyConflictPolicy` (`.keepDestination` or `.overwriteDestination`). Move operations take `PersistentKeyMoveConflictPolicy` (`.keepBoth`, `.overwriteDestination`, or `.keepDestinationAndRemoveSource`). Conflict policies do not apply to an item that rewrites a key in place within one store.
- **Completion tracking**: `PersistentKeyMigrationTracking` offers `.untracked`, `.once(id:)` (records `.isMigrationCompleted(id:)` in the destination store), and `.once(id:recordedIn:)`. Each marker key is `"PersistentKeyValueKit_MigrationCompleted_"` (containing no `.` characters) followed by the unpadded base64url-encoded SHA-256 digest of `id` normalized to Unicode Normalization Form C (NFC), producing an 84-UTF-16-code-unit key that `UserDefaults` key-value observation can observe directly and that fits within `NSUbiquitousKeyValueStore`'s 128-UTF-16-code-unit key limit for any `id`. Migration identifiers that compare equal as Swift strings share one marker, while case differences remain distinct. An empty batch (`[]`) is valid and records the completion marker when tracked. When recorded in `NSUbiquitousKeyValueStore`, iCloud syncs the marker like any other value: devices that receive it before migrating report `.alreadyRecorded` and skip the batch, while a device that runs first still performs the migration under its conflict policy. Use `.once(id:recordedIn: UserDefaults.standard)` to run a local-to-iCloud migration once per device. When migrating *from* `NSUbiquitousKeyValueStore`, a `.once` migration that runs before initial sync downloads remote values into the local cache sees absent sources (`.sourceAbsent`), records completion, and skips on later launches; run cloud-to-local migrations with `.untracked` until initial sync has completed or record completion under app control.
- **Structured reporting**: `copy` and `move` return `PersistentKeyMigrationReport` and are not `@discardableResult`. A report contains ordered `outcomes` (`[PersistentKeyMigrationReport.Outcome]`), `completion` (`Hashable`: `.recorded`, `.alreadyRecorded`, `.notRecorded`, `.failed`, or `.untracked`), `completionError: (any Error)?`, `hasFailures`, `isComplete`, `outcome(for:)` (matching `sourceKeyID` by literal UTF-16 code units), and `throwIfIncomplete()` (which throws `PersistentKeyMigrationIncompleteError` carrying `report`). Each `Outcome` has `sourceKeyID`, `destinationKeyID`, `status` (`Hashable`: `.copied`, `.moved`, `.rewritten`, `.keptDestination`, `.discardedSource`, `.sourceAbsent`, `.keyDisabled`, or `.failed(FailureStage)` at `.snapshot`, `.decode`, `.transform`, `.prepare`, `.write`, or `.cleanup`), and `error: (any Error)?`. Public initializers on `PersistentKeyMigrationReport` and `Outcome` support test fixtures and enforce with preconditions that `completionError` and `error` are non-`nil` if and only if the status is `.failed`, and that `outcomes` is empty for `.alreadyRecorded`, contains at least one failed outcome for `.notRecorded`, and contains no failed outcomes for `.recorded` or `.failed`.
- **Setup validation**: Setup errors (`PersistentKeyMigrationError`) are thrown before any key in the batch is read or modified, including `missingApplicationIdentifier`, `missingMigrationDomain`, `sameStore`, `duplicateKey(_:)`, `overlappingKeys(_:)`, `reservedKey(_:)` (for the `PersistentKeyValueKit_MigrationCompleted_` prefix), `keyIdentifierTooLong(_:)` (enforcing `NSUbiquitousKeyValueStore`'s 128-UTF-16-code-unit limit), `invalidMigrationIdentifier`, `overlappingMigration`, and `invalidCompletionRecord`. Errors thrown by a store's `migrationEndpoint` propagate unchanged.
- **Migratable named `UserDefaults` suites**: `UserDefaults.migratable(suiteName:)` creates a native `UserDefaults` instance with its suite name attached as process-local metadata for the lifetime of that instance. It returns `nil` if `suiteName` is empty, contains `/`, starts with `~`, ends with `.plist` (ignoring case, with `/`, `~`, and `.plist` checked by UTF-8 code units), matches (ignoring case and Unicode normalization) `argumentDomain`, `registrationDomain`, `globalDomain`, `kCFPreferencesAnyApplication`, `kCFPreferencesCurrentApplication`, or `Bundle.main.bundleIdentifier`, or cannot be created by Foundation. Migration treats suite names that differ only by case or Unicode normalization as the same store.
- **Per-key migration eligibility**: `PersistentKeyProtocol.isMigrationEnabled` controls whether a key participates in migration (`true` by default). `PersistentDebugKey` enables migration in Debug builds and disables it in Release builds, reporting `.keyDisabled`.

### Checked Representation Conversion

`PersistentKeyValueRepresentation` and `PrimitiveKeyValuePersistible` now expose throwing, format-aware conversion methods used by migration and direct validation:

- `PersistentKeyValueRepresentation.decode(storageObject:format:) throws -> Value`
- `PersistentKeyValueRepresentation.encode(_:format:) throws -> Any?`
- `PrimitiveKeyValuePersistible.decode(storageObject:format:) throws -> Self`
- `PrimitiveKeyValuePersistible.encode(format:) throws -> Any?`

`PersistentKeyValueStorageFormat` identifies `.propertyList`, `.userDefaults`, or `.ubiquitousKeyValueStore`. Built-in conversion failures throw `PersistentKeyValueConversionError` (`.invalidStorageValue`, `.invalidValue`, or `.encodingFailed`), while `CodablePersistentKeyValueRepresentation` rethrows the underlying `Encoder` and `Decoder` errors. Ordinary store `get` and `set` methods remain non-throwing.

`URL.encode(format:)` and `URL.decode(storageObject:format:)` support both absolute URLs and relative URL references, so relative references stored by 1.x continue to round-trip; when migrating a `URL` to `UserDefaults`, file URLs whose tilde-abbreviated path encoding cannot reproduce their `absoluteString` (such as a non-existent directory's trailing slash or a file URL host) fail at `.prepare` with `PersistentKeyValueConversionError.encodingFailed` before any store is modified. Checked conversion for `Array` and `Dictionary` (used by migration and `UserDefaults.register(_:)`) routes through the element or value representation's property-list container hooks (`get(from:)`, `set(_:to:)`, `get(_:from:)`, and `set(_:to:in:)`), so custom container formats round-trip across ordinary reads and writes, registration, and migration. Checked conversion fails if any array element or dictionary entry fails to decode, or if a stored Foundation dictionary (including nested dictionaries) has canonically equivalent keys with different UTF-16 spellings that would collapse into one Swift `String` key; ordinary `Dictionary` reads keep readable entries (omitting undecodable ones) and keep one entry when canonically equivalent keys collide (which one is unspecified).

### In-Memory Store Key Routing

`InMemoryPersistentKeyValueStore` now reads, writes, and removes values by calling the key's store-specific requirements on `PersistentKeyProtocol`, matching `UserDefaults` and `NSUbiquitousKeyValueStore`:

- `PersistentKeyProtocol.get(from: InMemoryPersistentKeyValueStore) -> Value`
- `PersistentKeyProtocol.set(to: Value, in: InMemoryPersistentKeyValueStore)`
- `PersistentKeyProtocol.remove(from: InMemoryPersistentKeyValueStore)`
- `InMemoryPersistentKeyValueStore.object(forKey:) -> Any?`
- `InMemoryPersistentKeyValueStore.set<Value>(_: Value, forKey:)`
- `InMemoryPersistentKeyValueStore.removeObject(forKey:)`

Each `PersistentKeyProtocol` requirement has a default implementation that reads, writes, or removes the Swift value under `id` through `object(forKey:)`, `set(_:forKey:)`, and `removeObject(forKey:)`. A key's value lives under its `id` in every store: store-specific `PersistentKeyProtocol` requirements customize how a value is read, written, or gated, while observation and migration read, write, and remove the entry under `id`. `set(_:forKey:)` compacts `nil` elements only out of Swift arrays and `String`-keyed dictionaries of optionals whose compacted result still has type `Value`, leaving Foundation collections such as `NSMutableArray` unchanged. Because the store retains and returns the Swift value itself, class-typed values are shared rather than copied and should be immutable or `Sendable` across concurrency domains; during migration, in-memory snapshots compare the contents of Foundation property-list objects and verify other reference types by revision only. Existing `PersistentKeyProtocol` conformers compile unchanged; only custom `PersistentKeyProtocol` conformers that want custom in-memory behavior need to implement those requirements or call the store's raw key accessors. Typed call sites continue to use `get(_:)`, `set(_:to:)`, and `remove(_:)`.

### Privacy Manifest

The `PersistentKeyValueKit` target now bundles an Apple privacy manifest (`PrivacyInfo.xcprivacy`) declaring `UserDefaults` access (`NSPrivacyAccessedAPICategoryUserDefaults`) with reasons `CA92.1` (app-sandbox preferences) and `1C8F.1` (app-group preferences).

## Breaking Changes and Upgrade Guide

### 1. Direct `PersistentKeyValueRepresentation` Conformances

`PersistentKeyValueRepresentation` now requires `decode(storageObject:format:)` and `encode(_:format:)`. Its eight store- and container-specific `get` and `set` methods now have default implementations built on those two methods; existing implementations continue to override them.

- **No changes required** if your types use `ProxyPersistentKeyValueRepresentation`, `RawRepresentablePersistentKeyValueRepresentation`, `CodablePersistentKeyValueRepresentation`, `LosslessStringConvertiblePersistentKeyValueRepresentation`, or conform to `ProxyPersistentKeyValueRepresentationProtocol`. `ProxyPersistentKeyValueRepresentationProtocol` provides default implementations backed by your existing `from(_:)` and `to(_:)` methods.
- **Action required** if you have a type that conforms directly to `PersistentKeyValueRepresentation`: implement `decode(storageObject:format:)` and `encode(_:format:)`. Return `nil` from `encode(_:format:)` when the key should be removed from the store (or omitted from a property-list array). The default `get` methods return `nil` on absence or decode failure and do not coerce `UserDefaults.argumentDomain` launch-argument strings; the default `set` methods remove the key when `encode` returns `nil` and leave the store or container unchanged when `encode` throws or returns a non-property-list object.

```swift
extension CustomRepresentation: PersistentKeyValueRepresentation {
    func decode(storageObject: Any, format: PersistentKeyValueStorageFormat) throws -> Value {
        guard let string = storageObject as? String, let value = Value(parsing: string) else {
            throw PersistentKeyValueConversionError.invalidStorageValue
        }
        return value
    }

    func encode(_ value: Value, format: PersistentKeyValueStorageFormat) throws -> Any? {
        value.serializedString
    }
}
```

### 2. Custom `PrimitiveKeyValuePersistible` Conformances

`PrimitiveKeyValuePersistible` now requires `static func decode(storageObject:format:)` and `func encode(format:)`. Its eight store- and container-specific `get` and `set` methods now have default implementations built on those two methods, using `.propertyList` for property-list arrays and dictionaries; existing implementations continue to override them. In 1.x, only the property-list array and dictionary methods had defaults, and they cast or assigned `Self` directly instead of routing through `decode` and `encode`. Custom primitives that relied on those 1.x container defaults now write container elements with `encode(format: .propertyList)` and read them with `decode(storageObject:format: .propertyList)`, so `decode` must accept any objects that 1.x persisted in property-list containers.

- **No changes required** for built-in primitive types (`Bool`, `Int`, `Float`, `Double`, `String`, `Data`, `URL`, `Array`, and `Dictionary`) or `Optional` (which uses `OptionalPersistentKeyValueRepresentation`).
- **Action required** if you conform a custom type to `PrimitiveKeyValuePersistible`:

```swift
extension CustomPrimitive: PrimitiveKeyValuePersistible {
    static func decode(storageObject: Any, format: PersistentKeyValueStorageFormat) throws -> Self {
        guard let number = storageObject as? NSNumber else {
            throw PersistentKeyValueConversionError.invalidStorageValue
        }
        return Self(rawValue: number.intValue)
    }

    func encode(format: PersistentKeyValueStorageFormat) throws -> Any? {
        NSNumber(value: rawValue)
    }
}
```

### 3. Custom `PersistentKeyValueStore` Conformances

`PersistentKeyValueStore` now requires `var migrationEndpoint: PersistentKeyValueMigrationEndpoint { get throws }`.

- **Action required** if you define a custom `PersistentKeyValueStore` wrapper or test double: forward your backing store's `migrationEndpoint`. A store that cannot participate in migrations can throw its own error from `migrationEndpoint`, which `copy` and `move` propagate unchanged.

```swift
extension ForwardingStore: PersistentKeyValueStore {
    var migrationEndpoint: PersistentKeyValueMigrationEndpoint {
        get throws {
            try base.migrationEndpoint
        }
    }
}
```

### 4. `URL` Storage Format in `NSUbiquitousKeyValueStore`

Writing a `URL` to `NSUbiquitousKeyValueStore` now stores `url.absoluteString` (`String`) instead of passing a `URL` instance directly to `NSUbiquitousKeyValueStore.set(_:forKey:)`. This matches `NSUbiquitousKeyValueStore`'s property-list storage requirements and `URL`'s `.propertyList` representation.

- Reading a `URL` from `NSUbiquitousKeyValueStore` in 2.0.0 accepts both `String` values and legacy `URL` objects written by 1.x.
- **Mixed-version iCloud compatibility**: 1.x clients read `URL` keys from `NSUbiquitousKeyValueStore` using `object(forKey:) as? URL`. If a device running 2.0.0 writes a `URL` to `NSUbiquitousKeyValueStore` (storing a `String`) and iCloud syncs that entry to a device still running 1.x, the 1.x client fails the cast to `URL` and returns the key's `defaultValue`.
- `UserDefaults` retains Foundation's native `URL` storage behavior (`UserDefaults.set(_ url: URL?, forKey:)` and `UserDefaults.url(forKey:)`), storing file URLs as tilde-abbreviated paths and non-file URLs as `NSKeyedArchiver` data.

### 5. All-or-Nothing Collection Writes and Property-List Array Replacement

In 1.x, `Array` and `Dictionary` writes persisted whichever elements or entries succeeded when another element failed to encode, and `URL.set(_:to:)`, `Array.set(_:to:)`, and `Dictionary.set(_:to:)`, along with `Optional` and proxy representations backed by those types, appended encoded elements to the `inout [Any]` parameter instead of replacing its contents. In 2.0.0:

- `Array` and `Dictionary` writes are all-or-nothing across `UserDefaults`, `NSUbiquitousKeyValueStore`, and property-list containers: if any element or entry fails to encode, the store or container is left unchanged instead of being overwritten with a partial collection. `Optional` `nil` elements and dictionary entries are still omitted intentionally.
- `set(_:to: inout [Any])` replaces `propertyListArray` with the encoded array across all built-in primitive types and representations instead of appending to existing elements. Callers (`Array`, `Dictionary`, `UserDefaults.register(_:)`, and migration) pass an empty `propertyListArray` to `set(_:to:)` and a dictionary that does not yet contain `dictionaryKey` to `set(_:to:in:)`, so custom 1.x implementations that append to `propertyListArray` continue to work alongside implementations that assign to it. Leaving `propertyListArray` empty for non-empty `values` (or leaving `dictionaryKey` absent) counts as an encoding failure unless `encode` returns `nil` for every element (or for the entry's value).
- Ordinary collection reads behave as in 1.x: `Array` reads are all-or-nothing (returning the key's `defaultValue` if any element fails to decode), and `Dictionary` reads keep readable entries and omit only undecodable ones so one unrecognized entry (such as an enum case written by a newer app version) does not blank the whole dictionary (keeping one entry if a stored Foundation dictionary has canonically equivalent keys with different UTF-16 spellings). Checked conversion (`decode(storageObject:format:)`, used by migration) routes through the element or value representation's container hooks and fails at `.decode` if any array element or dictionary entry fails to decode or if a stored dictionary's keys would collapse into one Swift `String` key, preserving the source entry.

### 6. Named `UserDefaults` Suites in Migrations

Any named `UserDefaults` suite that a migration reads or writes (as the receiver or `to:` destination of `copy` or `move`, or as the store passed to `.once(id:recordedIn:)`) must be created with `UserDefaults.migratable(suiteName:)`; `UserDefaults.standard` does not need it. Ordinary `UserDefaults(suiteName:)` instances elsewhere in your app continue to work unchanged for `get`, `set`, `remove`, `@PersistentValue`, and observation, but throw `PersistentKeyMigrationError.missingMigrationDomain` if used in a migration because Foundation does not expose an instance's writable suite name.

### 7. `PersistentDebugKey` in `InMemoryPersistentKeyValueStore` in Release Builds

In 1.x, `InMemoryPersistentKeyValueStore` accessed its storage directly by `key.id` without calling the key, so `PersistentDebugKey` remained mutable in `InMemoryPersistentKeyValueStore` in Release builds. In 2.0.0, `InMemoryPersistentKeyValueStore` routes `get(_:)`, `set(_:to:)`, and `remove(_:)` through `PersistentKeyProtocol`, and `PersistentDebugKey` applies its Release restriction to `InMemoryPersistentKeyValueStore` just like `UserDefaults` and `NSUbiquitousKeyValueStore`: in Release builds, `get` always returns the release default value and `set` and `remove` are no-ops.

- **Upgrade impact**: Tests or code compiled in Release mode (such as `swift test -c release`) that mutated a `PersistentDebugKey` in an `InMemoryPersistentKeyValueStore` now see the key's release default value instead of the written or removed value.
- **No changes required** for existing custom `PersistentKeyProtocol` conformances unless they want custom in-memory behavior, because `get(from:)`, `set(to:in:)`, and `remove(from:)` for `InMemoryPersistentKeyValueStore` provide default implementations. Custom `PersistentKeyProtocol` implementations must store the key's value under `id` in every store so observation and migration find the entry under `id`.

## Other Changes

- `@PersistentValue` now updates its observed key and store when a view is re-evaluated at the same identity with a different key (comparing key identifiers by literal UTF-16 code units), a different explicit `store:`, or a changed `defaultPersistentKeyValueStore` in the environment (previously it kept the initial key and store and wrote into them). A `$binding` projected from `@PersistentValue` captures the key and store active when the binding was created, so a retained binding continues reading and writing its original key and store after the view switches. `PersistentKeyUIObservableObject.key` is now `public private(set) var`.
- `UserDefaults.register(_:)` and `PersistentKeyProtocol.registerDefault(in:)` now encode default values with `.userDefaults` format instead of `.propertyList` (honoring custom property-list container hooks for arrays and dictionaries), so registered web `URL` defaults and custom representations with `UserDefaults`-specific encodings read back accurately through both typed `get(_:)` and `UserDefaults.url(forKey:)`. `UserDefaults.register(_:)` also preserves literal key identifiers, keeping canonically equivalent NFC and NFD spellings separate.
- `UserDefaults` launch-argument string coercion now applies only when the visible value is the literal key's `UserDefaults.argumentDomain` string and the key is not forced (`!objectIsForced(forKey:)`), so managed preferences take precedence over launch arguments per Apple's search order and a launch argument for one Unicode normalization form does not coerce a persisted string stored under another spelling.
- `UserDefaults` keys whose identifiers contain `.` are now observed across `@PersistentValue`, `PersistentKeyValues`, `PersistentKeyValuePublisher`, and `UserDefaults.register(observer:for:with:and:)` through a shared per-instance `UserDefaults.didChangeNotification` monitor that deduplicates reads and comparison values per literal key and serializes reconciliation outside its lock (so concurrent notifications can be delivered on the reconciling thread). Only in-process changes to the key's property-list value are delivered for dotted keys; cross-process writes and changes caused only by `addSuite(named:)` or `removeSuite(named:)` are not observed.
- `PersistentKeyValues` now emits the current state read from the store after each change in read order (never older than an already-emitted value), prevents changes reported during registration from being re-emitted out of order after the initial value, and reads values outside its lock; `.unbounded` buffers every observed value. When the iterating `Task` is cancelled before or during `next()`, `next()` deregisters and returns `nil` without returning a pending initial or buffered value, and subsequent calls on that iterator also return `nil`.
- `PersistentKeyValuePublisher` now reads the initial value when the publisher receives its subscriber and delivers it when initial demand is requested, delivers values synchronously on the thread that requests demand or reports a change (use `receive(on: DispatchQueue.main)` before updating UI), reads and decodes the store value outside its lock while preserving serialized delivery, rechecks cancellation after decoding so a subscription cancelled during a read does not deliver that value, releases subscriber references after unlocking so cancelling in `deinit` does not deadlock, and releases emitter ownership while holding its internal state lock so concurrent change notifications cannot be missed.
- `PersistentKeyValues`, `PersistentKeyValuePublisher`, and Foundation store observation ignore KVO or notification callbacks that arrive after observation has deregistered, and register observations before activating native listeners so a callback delivered during installation can deregister itself immediately.
- `NSUbiquitousKeyValueStore` observers (`@PersistentValue`, `PersistentKeyValues`, `PersistentKeyValuePublisher`, and `register(observer:for:with:and:)`) now refresh when an external change notification reports `NSUbiquitousKeyValueStoreAccountChange` or omits `NSUbiquitousKeyValueStoreChangedKeysKey`. `NSUbiquitousKeyValueStore.didChangeInternallyNotification` is posted with the writing `NSUbiquitousKeyValueStore` instance as the notification object, so local-write notifications reach observers registered on that same instance (use `NSUbiquitousKeyValueStore.default` everywhere, as Apple requires).
- `NSUbiquitousKeyValueStore.register(observer:for:with:and:)` and `deregister(_:for:context:)`, as well as `UserDefaults` dotted-key deregistration, are now tracked per observer, literal UTF-16 key identifier, and context and invoke `selector` only for notifications that may affect that literal key, so canonically equivalent NFC and NFD key spellings neither trigger nor deregister each other.
- `InMemoryPersistentKeyValueStore` now preserves an explicit entry when an optional key is set to `nil`, distinguishing a stored `nil` from an unset or removed key during migration. Migrating a stored `nil` from an in-memory store to `UserDefaults` or `NSUbiquitousKeyValueStore` with `.overwriteDestination` removes the destination key.
- `InMemoryPersistentKeyValueStore.get(_:)` now returns `key.defaultValue` instead of `nil` when an optional key with a non-`nil` default value has never been set or has been removed (in 1.x, `value as? Key.Value ?? key.defaultValue` matched `nil` against the optional `Key.Value` and discarded the default). Setting the key to `nil` still records an explicit `nil` entry that `get(_:)` returns as `nil`.
- `InMemoryPersistentKeyValueStore` now evaluates `key.id` before acquiring its lock and releases replaced or removed values after unlocking, preventing reentrancy deadlocks when a computed key identifier or a displaced value's `deinit` accesses the store.
