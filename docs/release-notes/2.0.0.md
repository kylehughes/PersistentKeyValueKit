# PersistentKeyValueKit 2.0.0 Release Notes

PersistentKeyValueKit 2.0.0 adds typed key migration between and within stores, introduces checked format-aware conversion on representations and primitive types, routes `InMemoryPersistentKeyValueStore` access through `PersistentKeyProtocol`, updates `URL` storage and validation, refines observation across SwiftUI, `AsyncSequence`, Combine, and Foundation stores, and bundles an Apple privacy manifest.

## What's New

### Store-to-Store and In-Place Key Migration

`PersistentKeyValueStore` now provides `copy` and `move` overloads for transferring a single key, a single `PersistentKeyMigrationItem`, a heterogeneous array of keys (`[any PersistentKeyProtocol]`), or a labeled array of items (`items: [PersistentKeyMigrationItem]`):

```swift
func makeAppGroupDefaults() throws -> UserDefaults? {
    guard let appGroup = UserDefaults.migratable(suiteName: "group.example.app") else {
        return nil
    }

    let report = try UserDefaults.standard.move(
        [.runtimeColorScheme, .launchCount],
        to: appGroup,
        onConflict: .keepBoth,
        tracking: .once(id: "app-group-preferences-v1")
    )
    try report.throwIfIncomplete()

    return appGroup
}
```

- **Key mapping and transforms**: `PersistentKeyMigrationItem` supports `.key(_:)`, `.key(_:to:)` for renaming a key of the same `Value` type, and `.key(_:to:transform:)` for converting values with an `@Sendable` throwing closure. `transform` runs after the source value decodes when both keys have `isMigrationEnabled == true` and the item will write to the destination (for an in-place rewrite, when the destination key has no persisted value, or when `onConflict` is `.overwriteDestination`). It is skipped when the source is absent (`.sourceAbsent`), either key has `isMigrationEnabled == false` (`.keyDisabled`, such as `PersistentDebugKey` in Release builds), or a conflict policy keeps the existing destination value (`.keptDestination` or `.discardedSource`). If the initial `transform` call throws, the item fails at stage `.transform` and the migration writes to neither store for that item, so a `move` keeps the source; because an `InMemoryPersistentKeyValueStore` source passes the stored Swift value itself to `transform` rather than a decoded copy, mutating a reference input in place (such as an `NSMutableArray`) mutates the stored source even if `transform` then throws, so copy a mutable input before changing it (if the verification replay of an in-place rewrite throws, the item fails at `.prepare` with `PersistentKeyMigrationError.nonIdempotentRewrite`).
- **Same-store migrations and in-place rewrites**: The source and destination can be the same store when every item either maps its source key to a different destination key or, in `UserDefaults` or `NSUbiquitousKeyValueStore`, rewrites a key in place through `.key(_:to:transform:)` on a single store instance with byte-identical source and destination key identifiers (`source.id.utf8.elementsEqual(destination.id.utf8)`). Duplicate source or destination key identifiers (including rewrites) throw `PersistentKeyMigrationError.duplicateKey(_:)`, and same-store batches where one item's destination is another item's source (such as `A` to `B` and `B` to `C`, or `A` to `B` and `B` to `A`) throw `PersistentKeyMigrationError.overlappingKeys(_:)`. `.key(_:)` and `.key(_:to:)`, a rewrite between two distinct instances for one backing store, or any same-store, same-ID item on `InMemoryPersistentKeyValueStore` (which does not support in-place rewrites; same-store renames to a different key identifier still work) throw `PersistentKeyMigrationError.sameStore` during setup, before any key is read. Key identity in duplicate, overlap, and same-store checks follows the store: `UserDefaults` and `NSUbiquitousKeyValueStore` compare identifiers by literal UTF-16 code units (treating NFC and NFD spellings as distinct keys), whereas `InMemoryPersistentKeyValueStore` is keyed by Swift `String` and treats canonically equivalent identifiers as one key.
- **Rewrite repeatability and retry safety**: An in-place rewrite decodes the stored value with the source key's representation, transforms it, encodes the result with the destination key's representation, replaces the stored value only if its snapshot has not changed, verifies the write, never removes the key as a source during a `move`, and reports `.rewritten` under every copy or move conflict policy (pass `transform: { $0 }` for a representation-only upgrade under the same key identifier). Before writing, the rewrite checks each reading of its prepared result (both the exact in-process object that the writing process reads back and its binary-property-list-serialized readback that other processes and later launches read, where an encoded `Int32` widens to a 64-bit integer that a source decoder may accept even if it rejects `Int32`): for each reading that decodes with the source key to a non-`nil` value, it runs `transform` and encodes again (so `transform` can run up to three times: the initial run plus replay against each reading), and unless every decoded reading reproduces the same stored value (failing if a replay throws or produces a different encoded value, such as `JSONEncoder` output without `.sortedKeys`), the item fails at `.prepare` with `PersistentKeyMigrationError.nonIdempotentRewrite` before mutating the store. In `UserDefaults` and `NSUbiquitousKeyValueStore`, numbers bridge across `NSNumber`, so overlapping numeric rewrites such as seconds to milliseconds (`Int` to `Double`) and dollars to cents are rejected at `.prepare` with `.nonIdempotentRewrite` (migrate to a new key identifier instead so a retry never reads its own result: a retry's behavior then depends on whether the source remains and whether the retry writes, so a `move` that removed its source finds no source value, `.keepDestination` and `.keepBoth` keep an existing destination value without running `transform` including a value an earlier attempt wrote while `.keepBoth` also leaves the source in place, and `.overwriteDestination` converts the source value again and replaces the earlier result), whereas `Int` to `String`, idempotent transforms, and identity representation-only rewrites with reproducible encoding (such as `.sortedKeys` for JSON when the source key can still decode the result) succeed. If a tracked batch is retried after a later item fails, a stored value that fails to decode with the source key's representation and decodes with the destination key's representation is treated as already rewritten: after rechecking that the stored snapshot has not changed while decoding (failing at `.write` with `PersistentKeyMigrationError.destinationChanged` if it changed), the item reports `.rewritten` without running `transform` or writing again.
- **Persisted-domain reads, snapshot verification, and cleanup reporting**: Migration inspects only values persisted in a store's own domain; registered defaults (`UserDefaults.register`), launch arguments (`UserDefaults.argumentDomain`), added suites (`UserDefaults.addSuite(named:)`), and a key's `defaultValue` are neither migrated nor treated as destination conflicts. `UserDefaults` migration snapshots read the writable domain as an unbridged `NSDictionary` so keys match by literal UTF-16 code units, and snapshots and prepared writes in `UserDefaults` and `NSUbiquitousKeyValueStore` hold exact immutable copies of the stored or encoded property-list objects (preserving each number's `CFNumber` type, including integer width and `NSDecimalNumber`) so migration decodes the same object an ordinary `get` reads and commits the same object an ordinary `set` writes. Snapshot verification compares property-list types, floating-point widths (`Float` versus `Double`), signed zeros (`0.0` versus `-0.0`), `NaN`, `Date` time-interval bit patterns (treating two `NaN` dates as equal so an unchanged `NaN` date verifies), and `NSDecimalNumber` values recursively: boolean `true` is not equal to integer `1`, an `NSDecimalNumber` is never equal to a `Double` or other non-decimal `NSNumber`, two decimals compare with exact decimal equality, and integers compare by value regardless of width because `UserDefaults` does not preserve integer width across processes or launches (an `Int32` written in one process reads back as written in that process, and as `Int64` elsewhere). Preparing a write to `UserDefaults` or `NSUbiquitousKeyValueStore` validates and copies the encoded object as an exact immutable property list (which `ProxyPersistentKeyValueRepresentationProtocol.encode(_:format:)` and `CodablePersistentKeyValueRepresentation.encode(_:format:)` also do, throwing `PersistentKeyValueConversionError.encodingFailed` when the encoding is not a property list), verifies that a binary-property-list-serialized copy still equals it, and commits the exact copy, failing at `.prepare` with `PersistentKeyValueConversionError.encodingFailed` before mutating either store when the encoded object is not a property list (such as an invalid or self-referential container) or when binary property-list serialization would change the value or stored type (for example, any `NSDecimalNumber`, including exact ones, because binary property-list serialization stores it as a `Double`, whereas integer width is not part of the stored type so an `Int32` does not fail). `InMemoryPersistentKeyValueStore` snapshots and prepared writes capture an exact immutable copy of Foundation property-list objects (such as `NSMutableArray`, including nested `NSDecimalNumber` values) to detect in-place edits, the verification snapshot for a committed write carries the copy captured when the write was prepared before the value is stored and observers are notified, and snapshot verification compares the current object's contents outside the lock and then rechecks under the lock that the stored entry still has the snapshot's revision (while other reference types are verified by revision only). A `UserDefaults` write or rewrite that replaces a stored object with a `CFEqual` object of a different property-list type removes the old object first and fails at `.write` with `.destinationChanged` (preserving the observer's write) if an observer writes the key during removal. On a `move`, a destination change detected before source removal under `.keepDestinationAndRemoveSource` fails at `.write` with `PersistentKeyMigrationError.destinationChanged` without removing the source, `.failed(.cleanup)` with `PersistentKeyMigrationError.sourceChanged` means the source no longer matched its initial snapshot before removal so the move did not remove it, and `.failed(.cleanup)` with `PersistentKeyMigrationError.destinationChanged` means the move had removed the source and does not roll back its destination write after the destination no longer matched its expected snapshot (for example, when an observer or concurrent writer modified or removed either store's value).
- **Conflict policies and completion tracking**: Every `copy` and `move` call requires an explicit conflict policy (`PersistentKeyCopyConflictPolicy.keepDestination` or `.overwriteDestination`; `PersistentKeyMoveConflictPolicy.keepBoth`, `.overwriteDestination`, or `.keepDestinationAndRemoveSource`) and tracking mode (`PersistentKeyMigrationTracking.untracked`, `.once(id:)` recorded in the destination store, or `.once(id:recordedIn:)`). Each completion marker key (`.isMigrationCompleted(id:)`) is `"PersistentKeyValueKit_MigrationCompleted_"` (containing no `.` characters) followed by the unpadded base64url-encoded SHA-256 digest of `id` normalized to Unicode Normalization Form C (NFC), producing an 84-UTF-16-code-unit key that `UserDefaults` key-value observation can observe directly and that fits within `NSUbiquitousKeyValueStore`'s 128-UTF-16-code-unit key limit for any `id`. Migration identifiers that compare equal as Swift strings share one marker, while case differences remain distinct. An empty batch (`[]`) is valid and records the completion marker when tracked. When recorded in `NSUbiquitousKeyValueStore`, iCloud syncs the marker across devices (use `.once(id:recordedIn: UserDefaults.standard)` for once-per-device seeding); when migrating *from* `NSUbiquitousKeyValueStore`, use `.untracked` until initial sync has populated the local cache so missing keys are not permanently recorded as `.sourceAbsent`.
- **Structured reporting and setup validation**: `copy` and `move` return `PersistentKeyMigrationReport` (not `@discardableResult`) with ordered `outcomes` (`[PersistentKeyMigrationReport.Outcome]`), `completion` (`Hashable`: `.recorded`, `.alreadyRecorded`, `.notRecorded`, `.failed`, or `.untracked`, where `.notRecorded` applies to `.once` modes when an item fails and `.untracked` always leaves `completion == .untracked`), `completionError: (any Error)?`, `hasFailures`, `isComplete` (`false` whenever any item or completion recording fails, including under `.untracked`), `outcome(for:)` (matching `sourceKeyID` by literal UTF-16 code units), and `throwIfIncomplete()` (throwing `PersistentKeyMigrationIncompleteError` carrying `report`). Each `Outcome` has `sourceKeyID`, `destinationKeyID`, `status` (`Hashable`: `.copied`, `.moved`, `.rewritten`, `.keptDestination`, `.discardedSource`, `.sourceAbsent`, `.keyDisabled`, or `.failed(FailureStage)` at `.snapshot`, `.decode`, `.transform`, `.prepare`, `.write`, or `.cleanup`), and `error: (any Error)?`. Public fixture initializers on `PersistentKeyMigrationReport`, `Outcome`, and `PersistentKeyMigrationIncompleteError` enforce with preconditions that `completionError` and `error` are non-`nil` if and only if the status is `.failed`, `outcomes` is empty for `.alreadyRecorded`, `outcomes` contains at least one failed outcome for `.notRecorded`, `outcomes` contains no failed outcomes for `.recorded` or `.failed`, and `PersistentKeyMigrationIncompleteError(report:)` receives an incomplete report (`!report.isComplete`). Setup errors (`PersistentKeyMigrationError`: `missingApplicationIdentifier`, `missingMigrationDomain`, `sameStore`, `duplicateKey(_:)`, `overlappingKeys(_:)`, `reservedKey(_:)`, `keyIdentifierTooLong(_:)`, `invalidMigrationIdentifier`, `overlappingMigration`, and `invalidCompletionRecord`, plus any error thrown by `migrationEndpoint`) are thrown before any key in the batch is read or modified.
- **Migratable named `UserDefaults` suites**: `UserDefaults.migratable(suiteName:)` creates a native `UserDefaults` instance with its suite name attached as process-local metadata for the lifetime of that instance. It returns `nil` if `suiteName` is empty, contains `/`, starts with `~`, ends with `.plist` (ignoring case, with `/`, `~`, and `.plist` checked by UTF-8 code units so combining marks cannot hide path or `.plist` delimiters), matches (ignoring case and Unicode normalization) `argumentDomain`, `registrationDomain`, `globalDomain`, `kCFPreferencesAnyApplication`, `kCFPreferencesCurrentApplication`, or `Bundle.main.bundleIdentifier`, or cannot be created by Foundation. Migration treats suite names that differ only by case or Unicode normalization as the same store.

### Checked Representation Conversion

`PersistentKeyValueRepresentation` and `PrimitiveKeyValuePersistible` now expose throwing, format-aware conversion methods used by migration, `UserDefaults.register(_:)`, and direct validation:

- `PersistentKeyValueRepresentation.decode(storageObject:format:) throws -> Value`
- `PersistentKeyValueRepresentation.encode(_:format:) throws -> Any?`
- `PrimitiveKeyValuePersistible.decode(storageObject:format:) throws -> Self`
- `PrimitiveKeyValuePersistible.encode(format:) throws -> Any?`

`PersistentKeyValueStorageFormat` identifies `.propertyList`, `.userDefaults`, or `.ubiquitousKeyValueStore`. Built-in conversion failures throw `PersistentKeyValueConversionError` (`.invalidStorageValue`, `.invalidValue`, or `.encodingFailed`), while `CodablePersistentKeyValueRepresentation` rethrows the underlying `Encoder` and `Decoder` errors. Checked `encode(_:format:)` on `ProxyPersistentKeyValueRepresentationProtocol` and `CodablePersistentKeyValueRepresentation` (and migration write preparation) validates and copies the encoded object with a throwing exact property-list copy (throwing `PersistentKeyValueConversionError.encodingFailed` when the encoding is not a valid property list) before validating that immutable Foundation-bridged deep copy with `decode(storageObject:format:)` and returning it, so a decoder that consumes or mutates writable input during validation cannot alter what is written. Ordinary store `get` and `set` methods remain non-throwing.

- **Container conversion**: Representations defined by the package (`Array`, `Dictionary`, `Optional`, `ProxyPersistentKeyValueRepresentation`, `RawRepresentablePersistentKeyValueRepresentation`, `LosslessStringConvertiblePersistentKeyValueRepresentation`, `CodablePersistentKeyValueRepresentation`, and built-in scalar primitives) convert property-list containers through strict, linear checked paths on any thread: checked array decoding finishes both storage decoding and proxy conversion for each element before reading the next and rethrows the first error in input order, while checked encoding converts proxy layers before encoding the resulting proxies (so an outer proxy conversion error on a later element can precede an inner encoding error on an earlier element). Representations defined outside the package (custom `PersistentKeyValueRepresentation` or `PrimitiveKeyValuePersistible` conformers, and consumer types conforming to `ProxyPersistentKeyValueRepresentationProtocol`) have their container methods (`get(from:)`, `set(_:to:)`, `get(_:from:)`, and `set(_:to:in:)`) called as written, whether overridden or inherited from the protocol default: a hook that drops undecodable elements drops them in migration too, a consumer type conforming to `ProxyPersistentKeyValueRepresentationProtocol` over a `[String: Value]` proxy with default container methods delegates to `[String: Value]`'s container methods and reads nested dictionaries leniently, and container failures throw the generic `PersistentKeyValueConversionError.encodingFailed` or `.invalidStorageValue`. Checked `Dictionary.decode` fails if any entry fails to decode or if a stored Foundation dictionary has canonically equivalent keys with different UTF-16 spellings that would collapse into one Swift `String` key, whereas ordinary `Dictionary` reads keep readable entries and keep one entry when canonically equivalent keys collide.
- **`URL` conversion**: `URL.encode(format:)` and `URL.decode(storageObject:format:)` support both absolute URLs and relative URL references. For `.userDefaults`, checked encoding (`URL.encode(format: .userDefaults)`) refuses file URLs whose tilde-abbreviated stored path cannot reproduce `url.absoluteString` (such as a file URL with a host or a nonexistent directory with a trailing slash), throwing `PersistentKeyValueConversionError.encodingFailed`. As a result, migrating such a URL to `UserDefaults` fails at `.prepare` before any store is modified across direct `URL` keys, `Optional<URL>`, and proxies over `URL`, and `UserDefaults.register(_:)` skips such default values (typed `get(_:)` still returns the key's `defaultValue`, while raw `UserDefaults.url(forKey:)` returns `nil` when no other value is visible). Ordinary `set` on `UserDefaults` keeps Foundation's lossy path behavior, and `[URL]` stores `absoluteString` values in `.propertyList` format and is unaffected.

### In-Memory Store Key Routing and Semantics

`InMemoryPersistentKeyValueStore` now reads, writes, and removes values by calling the key's store-specific requirements on `PersistentKeyProtocol`, matching `UserDefaults` and `NSUbiquitousKeyValueStore`:

- `PersistentKeyProtocol.get(from: InMemoryPersistentKeyValueStore) -> Value`
- `PersistentKeyProtocol.set(to: Value, in: InMemoryPersistentKeyValueStore)`
- `PersistentKeyProtocol.remove(from: InMemoryPersistentKeyValueStore)`
- `InMemoryPersistentKeyValueStore.object(forKey:) -> Any?`
- `InMemoryPersistentKeyValueStore.set<Value>(_: Value, forKey:)`
- `InMemoryPersistentKeyValueStore.removeObject(forKey:)`

Each `PersistentKeyProtocol` requirement has a default implementation that accesses the Swift value under `id` through `object(forKey:)`, `set(_:forKey:)`, and `removeObject(forKey:)`. A key's value lives under its `id` in every store: store-specific `PersistentKeyProtocol` requirements customize how a value is read, written, or gated, while observation and migration read, write, and remove the entry under `id`.

- `set(_:forKey:)` records an explicit entry when an optional key is set to `nil` (distinguishing a stored `nil` from an unset or removed key; migrating a stored `nil` to `UserDefaults` or `NSUbiquitousKeyValueStore` with `.overwriteDestination` removes the destination key) and compacts `nil` elements only out of Swift arrays and `String`-keyed dictionaries of optionals whose compacted result still has type `Value`, leaving Foundation collections such as `NSMutableArray` unchanged.
- `get(_:)` returns `key.defaultValue` when an optional key with a non-`nil` default value has never been set or has been removed, while returning `nil` when `nil` was explicitly stored.
- Because `InMemoryPersistentKeyValueStore` retains and returns the Swift value itself, class-typed values are shared rather than copied and should be immutable or `Sendable` across concurrency domains; migrations between in-memory stores transfer values by type cast without calling representation codecs.
- `InMemoryPersistentKeyValueStore` evaluates `key.id` before acquiring its lock and releases replaced, removed, or deallocated observer references after unlocking, preventing reentrancy deadlocks when a computed key identifier or a `deinit` accesses or deregisters from the store.

### Observation, Registration, and Launch Arguments

- **`@PersistentValue` updates and binding lifetime**: `@PersistentValue` now updates its observed key and store when a view is re-evaluated at the same identity with a different key (comparing key identifiers by literal UTF-16 code units; because `PersistentKeyProtocol.ID` is `String`, SwiftUI `ForEach(keys)` merges canonically equivalent NFC and NFD key identifiers, so identify rows by UTF-8 code units with `ForEach(keys, id: \.id.utf8CString)`; `\.self` is not a substitute because synthesized equality compares identifiers as strings and `PersistentKey` and `PersistentDebugKey` equality also compares `defaultValue`, recreating a row when only its default changes), a different explicit `store:`, or a changed `defaultPersistentKeyValueStore` in the environment. `PersistentKeyUIObservableObject.key` is now `public private(set) var`. Setting `PersistentKeyUIObservableObject.store` to a different store (or between `nil` and a store, or to a value-type store) registers the new observation before releasing the previous key, observation, and store and then sends `objectWillChange`, whereas reassigning the same reference-type store instance (or `nil` when already `nil`) is a no-op that keeps the existing observation and sends nothing. After the observed store or key changes, the observable object no longer sends notifications from the previous one, including notifications queued from other threads. Reading `PersistentKeyUIObservableObject.value` when `store` is `nil` (such as after setting `store = nil`) returns `key.defaultValue` in both Debug and Release builds, while setting `value` without a store discards the write and asserts in Debug builds. If code that runs during a key or store replacement (an `objectWillChange` subscriber, observer registration or removal, or a `deinit` triggered when the previous key, observation, or store is released) selects another store or key, the observer keeps only the latest selection and ends earlier observations. Setting `@PersistentValue` or `PersistentKeyUIObservableObject.value` captures the current key and store before sending `objectWillChange`, so a synchronous subscriber that switches the observed key or store does not redirect the write. A `$binding` projected from `@PersistentValue` captures the key and store active when the binding was created and references the view's observer weakly, so a retained binding continues reading and writing its original key and store without keeping later stores or the view's state alive.
- **`PersistentKeyValues` ordering, cancellation, and buffer release**: `PersistentKeyValues` emits the current state read from the store after each change in read order (never older than an already-emitted value), prevents changes reported during registration from being re-emitted out of order after the initial value, and reads values outside its lock; `.unbounded` buffers every observed value. When the iterating `Task` is cancelled before or during `next()`, `next()` deregisters, releases any pending initial or buffered values, and returns `nil`, with all subsequent calls returning `nil`.
- **`PersistentKeyValuePublisher` demand, threading, and cancellation**: `PersistentKeyValuePublisher` reads the initial value when the publisher receives its subscriber and delivers it when initial demand is requested, delivers values synchronously on the thread that requests demand or reports a change (or on the thread already delivering when a concurrent change arrives, so a setter returning does not mean its update has been delivered yet; use `receive(on: DispatchQueue.main)` before updating UI), reads and decodes the store value outside its lock while preserving serialized delivery, rechecks cancellation after decoding so a subscription cancelled during a read does not deliver that value, releases subscriber references after unlocking so cancelling in `deinit` does not deadlock, and releases emitter ownership while holding its internal state lock so concurrent change notifications cannot be missed.
- **`UserDefaults` notification-monitored key observation**: Keys that key-value observation cannot observe (empty keys, keys starting with `@`, keys containing a `.` code unit even inside a combined character, keys containing NUL, and the literal keys `valueForKey:` and `ValueForKey:`) are observed across `@PersistentValue`, `PersistentKeyValues`, `PersistentKeyValuePublisher`, and `UserDefaults.register(observer:for:with:and:)` through a shared per-instance `UserDefaults.didChangeNotification` monitor, while all other keys use key-value observation and also see other processes' changes. Each registration reads and keeps its own comparison value before `register` returns (a same-thread registration made during a pending first read, such as from an overridden getter, joins that read instead of reading again, and a change reported during the first read triggers another reconciliation pass). Each reconciliation pass reads each observed literal UTF-16 key once, notifies registrations that existed when the pass began whose comparison value differs from the read (reusing the comparison result across registrations that share the same comparison object reference, including `NSNumber`) or that joined while the reconciliation was in progress and had any change reported since they joined (even if the value read equals their comparison value, so a joining subscriber may receive one extra, possibly repeated, emission), and performs reads, Foundation property-list comparisons, observer callbacks, and observer releases outside its lock (as does `StoreKeyObservationRegistry`), preventing deadlocks under concurrent writes and iterator teardown. Changes are sampled rather than queued: a registration is notified only by reads made after it joins its key, multiple writes between reads give at most one notification, a change that is undone before it is sampled (`A` to `B` to `A`) can produce no notification for any subscriber, and consecutive emitted values can be equal. Only in-process changes to the key's property-list value are delivered for notification-monitored keys; cross-process writes and changes caused only by `addSuite(named:)` or `removeSuite(named:)` are not observed.
- **`NSUbiquitousKeyValueStore` observation**: Observers (`@PersistentValue`, `PersistentKeyValues`, `PersistentKeyValuePublisher`, and `register(observer:for:with:and:)`) refresh when an external change notification reports `NSUbiquitousKeyValueStoreAccountChange` or omits `NSUbiquitousKeyValueStoreChangedKeysKey`. `NSUbiquitousKeyValueStore.didChangeInternallyNotification` is posted with the writing `NSUbiquitousKeyValueStore` instance as the notification object, so local-write notifications reach observers registered on that same instance (use `NSUbiquitousKeyValueStore.default` everywhere, as Apple requires).
- **Literal key identity, tracking, and registration-time deregistration**: `PersistentKey` and `PersistentDebugKey` `Equatable` and `Hashable` conformances compare and hash their `id` by literal UTF-16 code units (`id.utf16`) alongside `defaultValue`, so canonically equivalent NFC and NFD spellings are distinct `Set` and `Dictionary` members, consistent with Foundation store key identity (whereas `InMemoryPersistentKeyValueStore` is keyed by Swift `String` and stores such spellings in one entry). `NSUbiquitousKeyValueStore` and notification-monitored `UserDefaults` observations are tracked per observer, literal UTF-16 key identifier, and context so canonically equivalent NFC and NFD key spellings neither trigger nor deregister each other. Observations are registered before native listeners are activated and ignore callbacks after deregistration, so a callback delivered during installation can deregister itself immediately.
- **`UserDefaults` registration and launch arguments**: `UserDefaults.register(_:)` and `PersistentKeyProtocol.registerDefault(in:)` encode default values with `.userDefaults` format (honoring custom property-list container hooks for arrays and dictionaries and skipping defaults that fail to encode) and preserve literal UTF-16 key identifiers. `UserDefaults` launch-argument string coercion applies only when the visible value is the literal key's `UserDefaults.argumentDomain` string and the key is not forced (`!objectIsForced(forKey:)`), so managed preferences take precedence over launch arguments per Apple's search order and a launch argument for one Unicode normalization form does not coerce a persisted string stored under another spelling.

### Privacy Manifest

The `PersistentKeyValueKit` target bundles an Apple privacy manifest (`PrivacyInfo.xcprivacy`) declaring `UserDefaults` access (`NSPrivacyAccessedAPICategoryUserDefaults`) with reasons `CA92.1` (app-sandbox preferences) and `1C8F.1` (app-group preferences).

## Breaking Changes and Upgrade Guide

### 1. Direct `PersistentKeyValueRepresentation` Conformances

`PersistentKeyValueRepresentation` now requires `decode(storageObject:format:)` and `encode(_:format:)`. Its eight store- and container-specific `get` and `set` methods now have default implementations built on those two methods; existing implementations continue to override them.

- **No changes required** if your types use `ProxyPersistentKeyValueRepresentation`, `RawRepresentablePersistentKeyValueRepresentation`, `CodablePersistentKeyValueRepresentation`, `LosslessStringConvertiblePersistentKeyValueRepresentation`, or conform to `ProxyPersistentKeyValueRepresentationProtocol`. `ProxyPersistentKeyValueRepresentationProtocol` provides default implementations backed by your existing `from(_:)` and `to(_:)` methods.
- **Action required** if you have a type that conforms directly to `PersistentKeyValueRepresentation`: implement `decode(storageObject:format:)` and `encode(_:format:)`. Return `nil` from `encode(_:format:)` when the key should be removed from the store. The default `get` methods return `nil` on absence or decode failure and do not coerce `UserDefaults.argumentDomain` launch-argument strings; the default `set` methods remove the key when `encode` returns `nil` and leave the store or container unchanged when `encode` throws or returns a non-property-list object.

```swift
extension CustomRepresentation: PersistentKeyValueRepresentation {
    func decode(storageObject: Any, format: PersistentKeyValueStorageFormat) throws -> Value {
        guard let string = storageObject as? String, let value = Value(parsing: string) else {
            throw PersistentKeyValueConversionError.invalidStorageValue
        }
        return value
    }

    func encode(_ value: Value, format: PersistentKeyValueStorageFormat) throws -> Any? {
        value.serializedString
    }
}
```

### 2. Custom `PrimitiveKeyValuePersistible` Conformances

`PrimitiveKeyValuePersistible` now requires `static func decode(storageObject:format:)` and `func encode(format:)`. Its eight store- and container-specific `get` and `set` methods now have default implementations built on those two methods, using `.propertyList` for property-list arrays and dictionaries; existing implementations continue to override them. In 1.x, only the property-list array and dictionary methods had defaults, and they cast or assigned `Self` directly instead of routing through `decode` and `encode`. Custom primitives that relied on those 1.x container defaults now write container elements with `encode(format: .propertyList)` and read them with `decode(storageObject:format: .propertyList)`, so `decode` must accept any objects that 1.x persisted in property-list containers.

- **No changes required** for built-in primitive types (`Bool`, `Int`, `Float`, `Double`, `String`, `Data`, `URL`, `Array`, and `Dictionary`) or `Optional` (which uses `OptionalPersistentKeyValueRepresentation`).
- **Action required** if you conform a custom type to `PrimitiveKeyValuePersistible`:

```swift
extension CustomPrimitive: PrimitiveKeyValuePersistible {
    static func decode(storageObject: Any, format: PersistentKeyValueStorageFormat) throws -> Self {
        guard let number = storageObject as? NSNumber else {
            throw PersistentKeyValueConversionError.invalidStorageValue
        }
        return Self(rawValue: number.intValue)
    }

    func encode(format: PersistentKeyValueStorageFormat) throws -> Any? {
        NSNumber(value: rawValue)
    }
}
```

### 3. Custom `PersistentKeyValueStore` Conformances

`PersistentKeyValueStore` now requires `var migrationEndpoint: PersistentKeyValueMigrationEndpoint { get throws }`.

- **Action required** if you define a custom `PersistentKeyValueStore` wrapper or test double: forward your backing store's `migrationEndpoint`. A store that cannot participate in migrations can throw its own error from `migrationEndpoint`, which `copy` and `move` propagate unchanged.

```swift
extension ForwardingStore: PersistentKeyValueStore {
    var migrationEndpoint: PersistentKeyValueMigrationEndpoint {
        get throws {
            try base.migrationEndpoint
        }
    }
}
```

### 4. `URL` Storage and Validation

Writing a `URL` to `NSUbiquitousKeyValueStore` now stores `url.absoluteString` (`String`) instead of passing a `URL` instance directly to `NSUbiquitousKeyValueStore.set(_:forKey:)`. This matches `NSUbiquitousKeyValueStore`'s property-list storage requirements and `URL`'s `.propertyList` representation.

- Reading a `URL` from `NSUbiquitousKeyValueStore` in 2.0.0 accepts both `String` values and legacy `URL` objects written by 1.x.
- **Mixed-version iCloud compatibility**: 1.x clients read `URL` keys from `NSUbiquitousKeyValueStore` using `object(forKey:) as? URL`. If a device running 2.0.0 writes a `URL` to `NSUbiquitousKeyValueStore` (storing a `String`) and iCloud syncs that entry to a device still running 1.x, the 1.x client fails the cast to `URL` and returns the key's `defaultValue`.
- `UserDefaults` retains Foundation's native `URL` storage behavior (`UserDefaults.set(_ url: URL?, forKey:)` and `UserDefaults.url(forKey:)`), storing file URLs as tilde-abbreviated paths and non-file URLs as `NSKeyedArchiver` data. Checked encoding for `.userDefaults` (used by migration and `UserDefaults.register(_:)`) throws `PersistentKeyValueConversionError.encodingFailed` for file URLs whose path cannot reproduce `url.absoluteString` (such as a file URL host or a nonexistent directory's trailing slash), including through `Optional` and proxy representations.

### 5. All-or-Nothing Collection Writes and Container Hooks

In 1.x, `Array` and `Dictionary` writes persisted whichever elements or entries succeeded when another element failed to encode, and `URL.set(_:to:)`, `Array.set(_:to:)`, and `Dictionary.set(_:to:)`, along with `Optional` and proxy representations backed by those types, appended encoded elements to the `inout [Any]` parameter instead of replacing its contents. In 2.0.0:

- `Array` and `Dictionary` writes are all-or-nothing across `UserDefaults`, `NSUbiquitousKeyValueStore`, and property-list containers: if any element or entry fails to encode, the store or container is left unchanged instead of being overwritten with a partial collection. `Optional` `nil` elements and dictionary entries are omitted through `OptionalPersistentKeyValueRepresentation` (built-in `Optional` and proxy representations convert each value once during ordinary collection writes and decide omission from that conversion before encoding the remaining values with `set(_:to:)` or `set(_:to:in:)`, keeping failed and omitted writes linear even on nested collections and proxies, with dictionary writes converting each entry through every wrapper layer before the next entry so the first failing entry stops the write).
- `set(_:to: inout [Any])` replaces `propertyListArray` with the encoded array across all built-in primitive types and representations instead of appending to existing elements. Callers (`Array`, `Dictionary`, `UserDefaults.register(_:)`, and migration) pass an empty `propertyListArray` to `set(_:to:)` and a dictionary that does not yet contain `dictionaryKey` to `set(_:to:in:)`, so custom 1.x implementations that append to `propertyListArray` continue to work alongside implementations that assign to it.
- For representations defined outside this package, leaving `propertyListArray` empty for non-empty `values` or leaving `dictionaryKey` absent counts as an encoding failure (even if the custom representation's `encode` returned `nil` for every array element or for the dictionary entry's value), leaving the store unchanged on ordinary writes and throwing `PersistentKeyValueConversionError.encodingFailed` in checked conversion.
- Ordinary collection reads behave as in 1.x: `Array` reads are all-or-nothing (returning the key's `defaultValue` if any element fails to decode), and `Dictionary` reads keep readable entries and omit undecodable ones. In checked conversion, representations defined by the package fail if any nested array element or dictionary entry fails to decode or if canonically equivalent dictionary keys collide, whereas representations defined outside the package run their container methods as written (so a custom hook that drops elements, or a consumer `ProxyPersistentKeyValueRepresentationProtocol` type over `[String: Value]` with default container methods, keeps that lenient behavior in migration too).

### 6. Named `UserDefaults` Suites in Migrations

Any named `UserDefaults` suite that a migration reads or writes (as the receiver or `to:` destination of `copy` or `move`, or as the store passed to `.once(id:recordedIn:)`) must be created with `UserDefaults.migratable(suiteName:)`; `UserDefaults.standard` does not need it (requiring a non-empty `Bundle.main.bundleIdentifier`, or throwing `PersistentKeyMigrationError.missingApplicationIdentifier`). Ordinary `UserDefaults(suiteName:)` instances elsewhere in your app continue to work unchanged for `get`, `set`, `remove`, `@PersistentValue`, and observation, but throw `PersistentKeyMigrationError.missingMigrationDomain` if used in a migration because Foundation does not expose an instance's writable suite name.

### 7. `PersistentDebugKey` and Optional Defaults in `InMemoryPersistentKeyValueStore`

In 1.x, `InMemoryPersistentKeyValueStore` accessed its storage directly by `key.id` without calling the key, so `PersistentDebugKey` remained mutable in `InMemoryPersistentKeyValueStore` in Release builds, and `get(_:)` on an unset optional key with a non-`nil` `defaultValue` returned `nil` instead of `defaultValue`. In 2.0.0:

- `InMemoryPersistentKeyValueStore` routes `get(_:)`, `set(_:to:)`, and `remove(_:)` through `PersistentKeyProtocol`, and `PersistentDebugKey` applies its Release restriction to `InMemoryPersistentKeyValueStore` just like `UserDefaults` and `NSUbiquitousKeyValueStore`: in Release builds, `get` always returns the release default value and `set` and `remove` are no-ops.
- Unset or removed optional keys in `InMemoryPersistentKeyValueStore` now return `key.defaultValue` (even when non-`nil`), while setting an optional key to `nil` records an explicit `nil` entry that `get(_:)` returns as `nil`.
- **No changes required** for existing custom `PersistentKeyProtocol` conformances unless they want custom in-memory behavior, because `get(from:)`, `set(to:in:)`, and `remove(from:)` for `InMemoryPersistentKeyValueStore` provide default implementations. Custom `PersistentKeyProtocol` implementations must store the key's value under `id` in every store so observation and migration find the entry under `id`.
