# PersistentKeyValueKit 2.0.0 Release Notes

PersistentKeyValueKit 2.0.0 adds typed key migration within and between stores, checked format-aware conversion on representations and primitive types, `PersistentKeyProtocol` routing on `InMemoryPersistentKeyValueStore`, updated `URL` and collection rules, observation refinements across SwiftUI, `AsyncSequence`, Combine, and Foundation stores, and an Apple privacy manifest. Custom `PersistentKeyValueRepresentation`, `PrimitiveKeyValuePersistible`, and `PersistentKeyValueStore` conformances require new members, and `URL`, collection, and in-memory optional semantics change; see [Breaking Changes and Upgrade Guide](#breaking-changes-and-upgrade-guide). The [API documentation](https://kylehughes.github.io/PersistentKeyValueKit) is the reference for the contracts and edge cases of the new APIs.

## What's New

### Key Migration

`PersistentKeyValueStore` adds `copy` and `move` overloads for migrating a single key, a single `PersistentKeyMigrationItem`, a heterogeneous array (`[any PersistentKeyProtocol]`), or a labeled array (`items: [PersistentKeyMigrationItem]`):

```swift
func makeAppGroupDefaults() throws -> UserDefaults? {
    guard let appGroup = UserDefaults.migratable(suiteName: "group.example.app") else {
        return nil
    }

    let report = try UserDefaults.standard.move(
        [.runtimeColorScheme, .launchCount],
        to: appGroup,
        onConflict: .keepBoth,
        tracking: .once(id: "app-group-preferences-v1")
    )
    try report.throwIfIncomplete()

    return appGroup
}
```

- `PersistentKeyMigrationItem` maps a key to itself (`.key(_:)`), to a renamed key of the same value type (`.key(_:to:)`), or to a key of another type through an `@Sendable` throwing `transform` (`.key(_:to:transform:)`).
- Within one store, source identifiers must be unique, destination identifiers must be unique, and the two sets must be disjoint. In-place rewrites are not supported, so to change a key's stored representation or value format, `move` it to a new key.
- `onConflict:` takes `PersistentKeyCopyConflictPolicy` or `PersistentKeyMoveConflictPolicy`. Migration reads and writes only values persisted in each store's own domain, so registered defaults, launch arguments, added suites, and `defaultValue` are ignored.
- `tracking:` takes `PersistentKeyMigrationTracking`: `.untracked`, `.once(id:)` (recorded in the destination), or `.once(id:recordedIn:)`. After setup succeeds, a true marker for that `id` in the selected recording store skips the whole batch.
- `copy` and `move` return a `PersistentKeyMigrationReport` with per-item outcomes, the completion state, and `throwIfIncomplete()`. Setup and completion-marker reads can throw before any item runs, and errors from a store's migration endpoint propagate unchanged. Per-item failures are reported while the remaining items continue.
- Create any named `UserDefaults` suite that takes part in a migration with `UserDefaults.migratable(suiteName:)`.
- Migrations do not roll back completed writes. Coordinate other writers, processes, and reentrant code that writes to a migrating store before you migrate.
- Sharing preferences requires the same App Group on each target (substitute its identifier for `group.example.app`), and `NSUbiquitousKeyValueStore` requires the iCloud Key-value storage capability on each app target that uses it, including for local reads and writes.
- Call `makeAppGroupDefaults()` only from the target that owns the legacy defaults. A target with nothing to move still records the shared marker, so the owning target's later call returns `.alreadyRecorded` and skips its migration even though `throwIfIncomplete()` succeeds. Other targets can open the shared suite directly, and one that also migrates values needs its own marker `id`.

The `copy`, `move`, `PersistentKeyMigrationTracking`, `PersistentKeyMigrationReport`, and `PersistentKeyMigrationError` documentation covers retries, failure stages, completion markers, iCloud timing, and coordination in detail.

### Checked Representation Conversion

- `PersistentKeyValueRepresentation` and `PrimitiveKeyValuePersistible` add throwing `decode(storageObject:format:)` and `encode(_:format:)` / `encode(format:)` methods taking `PersistentKeyValueStorageFormat` (`.propertyList`, `.userDefaults`, or `.ubiquitousKeyValueStore`). Ordinary `get` and `set` stay non-throwing, and conversion can run more than once for the same value.
- Built-in conversion failures throw `PersistentKeyValueConversionError`, though Foundation and codec errors can also propagate. Built-in checked collection decoding fails on an undecodable element or entry where an ordinary `Dictionary` read omits it, but a custom container reader can filter values.
- `URL` conversion supports absolute URLs and relative references. Checked `.userDefaults` encoding rejects a file URL whose stored path cannot reproduce its `absoluteString`.
- Custom representations run their container methods as written during checked conversion. The `PersistentKeyValueRepresentation`, `Array`, and `Dictionary` documentation covers the contracts.

### In-Memory Store Key Routing

`InMemoryPersistentKeyValueStore` now routes `get(_:)`, `set(_:to:)`, and `remove(_:)` through `PersistentKeyProtocol` (`get(from:)`, `set(to:in:)`, `remove(from:)`), so a custom key can gate or clamp in-memory access as it does for the Foundation stores. A key's value must live under `id` in every store so observation and migration act on the same entry.

### Privacy Manifest

The `PersistentKeyValueKit` target bundles `PrivacyInfo.xcprivacy` declaring `UserDefaults` access (`NSPrivacyAccessedAPICategoryUserDefaults`) with reasons `CA92.1` (app-sandbox preferences) and `1C8F.1` (app-group preferences).

## Breaking Changes and Upgrade Guide

### 1. Direct `PersistentKeyValueRepresentation` Conformances

`PersistentKeyValueRepresentation` now requires `decode(storageObject:format:)` and `encode(_:format:)`. Its eight store- and container-specific `get` and `set` methods have default implementations built on those two methods, and existing overrides still apply to ordinary reads and writes. Make `decode` accept the immutable Foundation form of each object your existing setter or encoder produces, and make `encode` produce objects your ordinary getter can read, because Foundation migration validates the encoded object with the checked methods while later ordinary reads still use your getter.

- **No changes required** if you use `ProxyPersistentKeyValueRepresentation`, `RawRepresentablePersistentKeyValueRepresentation`, `CodablePersistentKeyValueRepresentation`, or `LosslessStringConvertiblePersistentKeyValueRepresentation`. A `ProxyPersistentKeyValueRepresentationProtocol` conformer inherits checked conversion and needs no changes unless it overrides ordinary store access, in which case verify in each supported format that checked decoding accepts objects your setter wrote and that your getter reads objects checked encoding produces.
- **Registration change**: `UserDefaults.register(_:)` in 1.x registered every representation's default through its dictionary-entry setter. In 2.0.0 it registers the object that checked `.userDefaults` encoding produces. If raw `UserDefaults` clients read a format your 1.x setter customized, reproduce it in your `.userDefaults` encoding. This also applies to a proxy that customized only the dictionary setter.
- **Upgrade steps**: Implement `decode(storageObject:format:)` and `encode(_:format:)`. The default Foundation setters still remove the entry when `encode` returns `nil`, and collections apply their own encoding rules. After a successful migration write to `UserDefaults` or `NSUbiquitousKeyValueStore`, the destination entry is absent only when the key's top-level encoding is `nil` and the value is `nil` at an actual `Optional` layer. A type-changing `UserDefaults` replacement can temporarily remove the old entry before storing the new object. Any other top-level value that encodes to `nil` fails that item at `.prepare`, writing neither entry. Do not mutate objects returned from `encode` or written by `set` afterward.
- **Default isolation**: In a target whose default isolation is `MainActor`, make the conversion witnesses usable from nonisolated code. Declaring the extension `nonisolated`, as below, does that, and individually `nonisolated` witnesses can preserve the rest of the type's isolation.

```swift
nonisolated extension CustomRepresentation: PersistentKeyValueRepresentation {
    func decode(storageObject: Any, format: PersistentKeyValueStorageFormat) throws -> Value {
        guard let string = storageObject as? String, let value = Value(parsing: string) else {
            throw PersistentKeyValueConversionError.invalidStorageValue
        }
        return value
    }

    func encode(_ value: Value, format: PersistentKeyValueStorageFormat) throws -> Any? {
        value.serializedString
    }
}
```

### 2. Custom `PrimitiveKeyValuePersistible` Conformances

`PrimitiveKeyValuePersistible` now requires `static func decode(storageObject:format:)` and `func encode(format:)`. Its eight store- and container-specific `get` and `set` methods have default implementations built on those two methods, using `.propertyList` for containers, and existing overrides still apply to ordinary reads and writes. The same `decode` and `encode` guidance as for representations applies.

- **No changes required** for built-in primitive types (`Bool`, `Int`, `Float`, `Double`, `String`, `Data`, `URL`, `Array`, and `Dictionary`) or `Optional`.
- **Registration change**: A primitive whose 1.x dictionary-entry setter customized the format that `UserDefaults.register(_:)` registered must reproduce that format in `encode(format: .userDefaults)` if raw `UserDefaults` clients read it.
- **Container change**: Custom primitives using 1.x container defaults now write and read container elements through `encode(format: .propertyList)` and `decode(storageObject:format: .propertyList)`, so `decode` must accept any objects 1.x persisted in containers.
- **Upgrade steps**: Implement `decode(storageObject:format:)` and `encode(format:)`. In a target whose default isolation is `MainActor`, make the conversion witnesses usable from nonisolated code, as below, or mark individual witnesses and the members they call `nonisolated`.

```swift
nonisolated extension CustomPrimitive: PrimitiveKeyValuePersistible {
    static func decode(storageObject: Any, format: PersistentKeyValueStorageFormat) throws -> Self {
        Self(rawValue: try Int.decode(storageObject: storageObject, format: format))
    }

    func encode(format: PersistentKeyValueStorageFormat) throws -> Any? {
        NSNumber(value: rawValue)
    }
}
```

### 3. Custom `PersistentKeyValueStore` Conformances

`PersistentKeyValueStore` now requires `var migrationEndpoint: PersistentKeyValueMigrationEndpoint { get throws }`.

- **Upgrade steps**: Forward your backing store's `migrationEndpoint` (`try base.migrationEndpoint`), or throw your own error if the store cannot migrate (`copy` and `move` propagate it unchanged). Forwarding makes migration read and write the backing store directly, bypassing the wrapper's and the keys' ordinary accessors.
- A store used with observation must support concurrent access, including to any mutable state a forwarding wrapper adds.
- In a target whose default isolation is `MainActor`, a nonisolated function can pass the store to `PersistentKeyValues`, `copy`, or `move` only if its conformance is nonisolated. Declaring the wrapper `nonisolated` (`nonisolated struct ForwardingStore` for the extension below) provides that, and a wrapper whose protocol methods and `migrationEndpoint` are individually `nonisolated` also works.

```swift
extension ForwardingStore: PersistentKeyValueStore {
    var migrationEndpoint: PersistentKeyValueMigrationEndpoint {
        get throws {
            try base.migrationEndpoint
        }
    }
}
```

### 4. `URL` Storage and Validation

1.x passed a raw `URL` to the `NSUbiquitousKeyValueStore` setter, which is not a property-list type. Writing a `URL` there now stores `url.absoluteString` (`String`).

- Reading a `URL` from `NSUbiquitousKeyValueStore` accepts `String` values and a raw `URL` if the store returns one.
- **Mixed-version iCloud compatibility**: 1.x clients read `URL` keys using `object(forKey:) as? URL`. When a 2.0.0 device writes a `URL` (`String`) and iCloud syncs it to a 1.x device, the 1.x client falls back to `defaultValue`.
- **Registered defaults**: 1.x registered a `URL` default as its `absoluteString` (`String`). `UserDefaults.register(_:)` in 2.0.0 registers a representable file URL as a path and a non-file URL as archive data, so raw `string(forKey:)` on a registered non-file `URL` default now returns `nil`. Use `url(forKey:)` for raw access.
- **Typed reads of registered URLs**: Typed reads of an unset key with a visible registered `URL` default change too. On macOS, the 1.2.3 typed getter read a registered HTTPS string as a local file path, while 2.0.0 returns the HTTPS URL.
- Ordinary `UserDefaults` `set` still uses Foundation's URL setter and keeps its storage, so a file URL with no path, such as `file:`, can remove the entry, and `file://localhost` stores an unreadable empty path. The `URL` documentation covers these cases.

### 5. All-or-Nothing Collection Writes and Container Contracts

In 1.x, failed collection writes could overwrite part of a collection, and the built-in `URL`, `Array`, and `Dictionary` implementations of `set(_:to: inout [Any])` appended to `propertyListArray` instead of replacing it.

- `Array` and `Dictionary` writes are now all-or-nothing across `UserDefaults`, `NSUbiquitousKeyValueStore`, and property-list containers, leaving the store unchanged if any element or entry fails to encode. `Optional` `nil` elements and entries are omitted.
- The built-in `URL`, `Array`, and `Dictionary` writers that previously appended now replace `propertyListArray`. The package passes an empty array to `set(_:to:)` and a dictionary missing `dictionaryKey` to `set(_:to:in:)`, so 1.x appending overrides stay compatible.
- **Handover contract**: Do not mutate an object after returning it from `encode`, returning it from a proxy `to`, or writing it via `set`, including mutable strings, data buffers, dictionary keys, and containers. Behavior is unspecified otherwise.
- **Container hook contracts**: Array `set(_:to:)` hooks must build the encoded array separately, assign or append it to the empty array only after every element succeeds, and leave that array empty on failure. Dictionary `set(_:to:in:)` hooks must write only `dictionaryKey`.
- **Reads**: An ordinary `Array` read of built-in element representations is all-or-nothing, and an ordinary `Dictionary` read omits undecodable entries. Saving a decoded collection back replaces the stored one, so an older client can erase entries it could not decode. The `Array` and `Dictionary` documentation has the details.

### 6. Named `UserDefaults` Suites in Migrations

- Create any named `UserDefaults` suite passed to `copy`, `move`, or `.once(id:recordedIn:)` with `UserDefaults.migratable(suiteName:)`. `UserDefaults.standard` requires a non-empty `Bundle.main.bundleIdentifier`, otherwise migration throws `.missingApplicationIdentifier`.
- Ordinary `UserDefaults(suiteName:)` instances keep working outside migrations, but throw `PersistentKeyMigrationError.missingMigrationDomain` if used in a migration.

### 7. `PersistentDebugKey`, In-Memory Optionals, and Key Access

- `InMemoryPersistentKeyValueStore` routes through `PersistentKeyProtocol`, so it applies `PersistentDebugKey`'s Release lock and skips migration with `.keyDisabled`. Custom `PersistentKeyProtocol` types get in-memory defaults.
- Unset or removed optional keys in `InMemoryPersistentKeyValueStore` now return `key.defaultValue` (even when non-`nil`), whereas setting an optional key to `nil` through the default in-memory setter records an explicit `nil` that `get(_:)` returns. A key can override that setter, and a `PersistentDebugKey` in Release builds ignores the write.
- The default in-memory setter now keeps a mutable Foundation array or dictionary as the original object, where 1.x stored a bridged Swift copy. Mutating it changes later reads without notifying observers.
- `PersistentKey` and `PersistentDebugKey` `Equatable` and `Hashable` now compare `id` by literal UTF-16 code units, and `PersistentKeyUIObservableObject.key` is now `public private(set) var`.

## Behavior Changes from 1.x

### Key Identity

- `UserDefaults`, `NSUbiquitousKeyValueStore`, `PersistentKey`, and `PersistentDebugKey` compare and hash key identifiers by literal UTF-16 code units, so composed and decomposed spellings, and identifiers that differ only in unpaired surrogates, stay distinct keys. `InMemoryPersistentKeyValueStore` merges them, so a test that needs them distinct needs a Foundation store.
- `PersistentKeyProtocol.ID` is `String`, which treats canonically equivalent spellings as equal, so use `ForEach(keys, id: \.id.utf8CString)` to keep them distinct in SwiftUI. The `PersistentKeyProtocol.id` documentation covers the limits of that workaround.

### SwiftUI

- `@PersistentValue` adopts the latest key on each view update and replaces its observation when the key identifier or the selected store changes. An explicit `store:` takes precedence over the `defaultPersistentKeyValueStore` environment value.
- Assigning a different `store` to `PersistentKeyUIObservableObject` updates observation, stops notifications from the previous store, and sends `objectWillChange`. Reassigning the same store instance keeps its existing registration. Reading `value` without a store returns `key.defaultValue`, and writing without a store is discarded and asserts in Debug builds.
- A `$binding` captures the active key and store when it is created, so a retained binding keeps reading and writing its original key and store after the view switches. A `value` write uses the key and store selected when its setter starts, even if a subscriber switches stores.

### Async and Combine Observation

- When `next()` observes cancellation of the iterating `Task`, it deregisters, releases pending and buffered values, and returns `nil`.
- `PersistentKeyValues` emits values read from the store in read order, defaulting to `.bufferingNewest(1)`, and several store change reports can produce one read and one emitted value.
- `PersistentKeyValuePublisher` reads the current value on subscription and delivers it on first demand. Delivery is serial for each subscription, can occur on a background thread, and does not schedule on a queue, so use `.receive(on: DispatchQueue.main)` before updating UI. During `receive(subscription:)`, only the subscribing thread delivers, so blocking there while waiting for another thread to deliver a value deadlocks.

### Foundation Stores

- `UserDefaults` keys that key-value observation cannot observe (empty keys, a leading `@`, a `.`, NUL, and `valueForKey:` / `ValueForKey:`) now observe through `UserDefaults.didChangeNotification` across all observation APIs. Changes are sampled, so rapid writes coalesce and a change undone before sampling can emit nothing.
- Other `UserDefaults` keys keep key-value observation and see cross-process changes, but Foundation posts nothing for a write that compares equal under Foundation equality (such as `Int64` over an equal `Int32`).
- A manual `NSUbiquitousKeyValueStore` observer's selector now receives changes only for its registered literal key, whereas 1.x delivered every change notification from the store. Observers refresh every key on an account change or a missing or unusable changed-keys list.
- Manual deregistration removes one native `UserDefaults` key-value observation registration per call. Notification-backed keys and the iCloud and in-memory stores remove every registration with the same observer, key, and context. In `NSUbiquitousKeyValueStore`, deregistration did nothing in 1.0.0 and removed all of an observer's registrations in 1.1.0 through 1.2.3, so each key and context pair now needs its own call. In memory, an earlier callback can now deregister a later observer before its pending callback runs. A manual `UserDefaults` observer receives `observeValue(forKeyPath:of:change:context:)` for its registered keys only.
- Deregister before you release a manual observer, because a notification-backed key can keep being sampled until its registration is removed.

### Registration and Launch Arguments

- `UserDefaults.register(_:)` and `registerDefault(in:)` encode defaults with `.userDefaults` format and skip a default that fails checked encoding. Typed reads decode a visible registered object, so the result can differ from `defaultValue` when encoding loses information, such as an array encoding that omits `nil` elements.
- The registration domain is volatile, so register on every launch in each app or extension process. Every `UserDefaults` instance in the process shares it, so registering the same identifier in another suite can replace its fallback.
- `register(_:)` preserves literal UTF-16 keys, whereas `registerDefault(in:)` fills a Swift dictionary that merges canonically equivalent spellings.
- Launch-argument coercion applies only when the visible value is the literal key's `UserDefaults.argumentDomain` string and no managed preference overrides it, so a launch argument for one Unicode spelling does not coerce a value stored under another.
